# Эксплуатационные скрипты HLA

Этот каталог содержит эксплуатационные скрипты для:

- публикации авторитетной файловой базы в отдельное Viewer-зеркало;
- отдельной зеркализации локальной папки с Word-заключениями в сетевую папку с помощью `robocopy`;
- автоматического резервного копирования PostgreSQL в один или несколько локальных скрытых файлов резервной копии;
- автоматического обновления локальной PostgreSQL из удалённой PostgreSQL;
- чистой инициализации ACL/EFS-защиты схемы 4 в явном профиле `domain_network` или `local_single_host`;
- установки отдельной службы Writer EFS на сервере каждого физического EFS-корня;
- редкого ручного транзакционного обновления Viewer-ПК;
- регистрации соответствующих задач в Планировщике заданий Windows.

Если скрипты берутся из собранного дистрибутива приложения, после автономной сборки Nuitka они находятся в каталоге: `dist-nuitka\HLA_Laboratory_System\Scripts\`

Если приложение установлено на боевом ПК целиком в каталог `C:\Program Files\HLA_Laboratory_System`, эти скрипты можно использовать прямо по пути: `C:\Program Files\HLA_Laboratory_System\Scripts`

Сценарии инициализации запускаются локально на узле физического корня. В `domain_network` ACL-зеркализация запускается выделенным узлом лабораторной инфраструктуры; только зеркализация файловой базы в EFS-режиме инициируется локальной задачей на сервере физического зеркала и выполняется уже работающей там службой Writer. В `local_single_host` сценарии и задачи зеркалирования файловой базы запрещены, а один локальный Writer EFS обслуживает один UUID корня роли `authoritative` только при наличии Laboratory-изменений; для профиля только с Viewer отдельный Writer не устанавливается. В EFS-режиме резервное копирование PostgreSQL передаёт Writer отдельную типизированную публикацию `BACKUP`. `Update\HLA_ProgramFiles_RemoteUpdate.ps1` — отдельный ручной инструмент распространения окончательной сборки Viewer.

В любой сборке Viewer с `ENABLE_LABORATORY_ACTIONS=False` скрипты и задачи Планировщика из этого каталога не устанавливаются, а каталоги `Scripts` и `HLA_FileBase_Writer` удаляются из комплекта Viewer. В `domain_network` Viewer читает отдельное зеркало. В `local_single_host` локальный Viewer читает тот же корень роли `authoritative` на единственном ПК, но не создаёт зеркало и не получает права изменения.

`ENABLE_FILE_BASE_ENCRYPTION` меняет инициализацию корня и путь физических изменений. При ACL приложения Laboratory и обслуживающие задачи пишут через общий служебный контур NTFS: по SMB в `domain_network` либо в единственный локальный корень роли `authoritative` под фактической служебной учётной записью в `local_single_host`. При EFS изменения файловой базы выполняет Writer, локальный для соответствующего физического корня. Зеркализация Word-заключений, копирование PostgreSQL между серверами и ручное обновление программных файлов Viewer не используют этот контур.

Файлы `.ps1` и `.psm1` в этом каталоге рассчитаны на штатный Windows PowerShell 5.1 в Windows 10 (включая 1809) и Windows 11. Эксплуатационные задачи запускаются с исходным `-ExecutionPolicy Bypass`; это не заменяет контроль доступа к утверждённому дистрибутиву и каталогам установки. Текст PowerShell-файлов намеренно должен оставаться в диапазоне ASCII без BOM: не добавляйте в них кириллицу, типографские кавычки и другие не-ASCII символы. Это ограничение не относится к `README.md`.

В примерах PowerShell значения вида `'<ИМЯ_ПАРАМЕТРА>'` — обязательные русскоязычные заполнители. Они всегда находятся внутри одинарных кавычек, поэтому блок остаётся синтаксически корректным, но перед выполнением значение нужно заменить целиком. Блоки, способные изменить данные или конфигурацию, проверяют такие значения до первой изменяющей команды:

```powershell
$Value = '<ИМЯ_ПАРАМЕТРА>'
if (@($Value) -match '<[^<>]+>') {
    throw 'Замените значения в угловых скобках перед запуском.'
}
```

Фиксированные пути установки HLA, имена скриптов и задач, а также канонические алиасы `HLA-FB` и `HLA-VIEW` являются частью эксплуатационного контракта и заполнителями не заменяются. Пароли никогда не записывайте вместо заполнителя: вводите их только через скрытый интерактивный запрос.

## Матрица сборок и узлов развёртывания

`FILE_BASE_DEPLOYMENT_MODE` является четвёртым неизменяемым измерением, заданным при сборке, и явно передаётся каждому связанному с файловой базой установщику или исполняемому компоненту как `-DeploymentMode`; независимые зеркализация Word-заключений, удалённое копирование PostgreSQL и средство обновления Viewer к этому профилю не привязаны. Таблица ниже описывает восемь сочетаний остальных переключателей для `domain_network`. Для `local_single_host` разрешён только один локальный корень роли `authoritative`: Laboratory использует соответствующую ACL/EFS-ветку, локальный Viewer читает тот же корень, зеркало файловой базы отсутствует, а резервное копирование PostgreSQL получает `-DeploymentMode local_single_host`.

| `ENABLE_LABORATORY_ACTIONS` | `ENABLE_FILE_BASE_ENCRYPTION` | `IMPORT_DB_STAGE_MODE` | GUI и файловая база | PostgreSQL и применимые узлы `Scripts` |
|---|---|---|---|---|
| `True` | `False` | `False` | Laboratory читает и изменяет авторитетный ACL-корень | резервное копирование одной явно заданной БД на узле авторитетного корня; ACL-зеркализация — на выделенном узле с доступом к обоим UNC |
| `True` | `False` | `True` | Laboratory читает и изменяет авторитетный ACL-корень | одна задача резервного копирования для `hla_db_before` и `hla_db_after`; ACL-зеркализация — на выделенном узле с доступом к обоим UNC |
| `True` | `True` | `False` | Laboratory читает авторитетный EFS-корень и передаёт изменения Writer на его сервере | резервное копирование одной явно заданной БД на сервере Writer авторитетного корня; EFS-зеркализация — отдельная задача `SYSTEM` на сервере Writer зеркала |
| `True` | `True` | `True` | Laboratory читает авторитетный EFS-корень и передаёт изменения Writer на его сервере | одна задача резервного копирования обеих БД этапов «до» и «после» на сервере Writer авторитетного корня; EFS-зеркализация — отдельная задача `SYSTEM` на сервере Writer зеркала |
| `False` | `False` | `False` | Viewer только читает ACL-зеркало; на Viewer-ПК нет `Scripts` и Writer | одна явно сопоставленная локальная БД; копирование PostgreSQL, если нужно, работает на отдельном узле автоматизации |
| `False` | `False` | `True` | Viewer только читает ACL-зеркало; на Viewer-ПК нет `Scripts` и Writer | локальные `hla_db_before` и `hla_db_after`; двухэтапное копирование, если нужно, работает на отдельном узле автоматизации PostgreSQL |
| `False` | `True` | `False` | Viewer только читает EFS-зеркало своим разрешённым сертификатом; на Viewer-ПК нет `Scripts` и Writer | одна явно сопоставленная локальная БД; копирование PostgreSQL, если нужно, работает на отдельном узле автоматизации |
| `False` | `True` | `True` | Viewer только читает EFS-зеркало своим разрешённым сертификатом; на Viewer-ПК нет `Scripts` и Writer | локальные `hla_db_before` и `hla_db_after`; двухэтапное копирование, если нужно, работает на отдельном узле автоматизации PostgreSQL |

Режим защиты авторитетного корня и зеркала обязан совпадать. Строки с `ENABLE_LABORATORY_ACTIONS=False` описывают Viewer-ПК, но сервер физического зеркала является отдельным инфраструктурным узлом: на нём находятся корень, серверные скрипты и, для EFS, Writer. Аналогично, узел удалённого копирования — отдельный Windows-узел автоматизации рядом с целевой PostgreSQL; `LocalDbHost=localhost` означает PostgreSQL на этом узле. Если целевая PostgreSQL расположена на другом сервере, задайте её точный адрес через `-LocalDbHost`, но не возвращайте каталог `Scripts` в комплект Viewer.

`IMPORT_DB_STAGE_MODE` не меняет служебный контур файловой базы, а `ENABLE_FILE_BASE_ENCRYPTION` не меняет пары PostgreSQL. Поэтому для каждого варианта применяется одна и та же инструкция выбранной ACL/EFS-ветки и одна инструкция выбранной обычной или двухэтапной ветки, а не восемь разных копий команд.

### Назначение

- `Encryption\Initialize-HLA-FileBaseEncryption.ps1`: создаёт `.hla_internal` схемы 4, постоянные ACL и, при выбранном режиме, EFS-политику чистого локального NTFS-корня; подробная инструкция находится в [`Encryption\README.md`](Encryption/README.md).
- `Encryption\HLA_FileBase_Encryption_Common.psm1`: единое внутреннее средство проверки манифеста, физической идентичности, ACL, журнала и EFS-получателей; напрямую не запускается.
- `Encryption\Export-HLA-EfsOperatorCertificates.ps1`: атомарно экспортирует проверенное поколение открытых EFS-сертификатов участников группы AD.
- `Install-HLA-FileBaseWriterService.ps1`: устанавливает Writer EFS на чистом сервере физического EFS-корня.
- `HLA_FileBase_LocalToNetwork_Mirror.ps1`: публикует авторитетный корень в независимо инициализированное Viewer-зеркало.
- `Install-HLA-FileBaseMirrorTask.ps1`: регистрирует задачу Планировщика Windows, которая запускает основной скрипт автоматически при старте компьютера.
- `HLA_WordConclusions_LocalToNetwork_Mirror.ps1`: непрерывно отслеживает изменения в локальной папке с Word-заключениями и зеркалирует их в сетевую папку.
- `Install-HLA-WordConclusionsMirrorTask.ps1`: регистрирует задачу Планировщика Windows, которая запускает сценарий зеркализации Word-заключений автоматически при старте компьютера.
- `HLA_Postgres_AutoBackup.ps1`: непрерывно отслеживает активность записи в PostgreSQL и обновляет скрытый файл резервной копии после завершения серии изменений.
- `Install-HLA-PostgresBackupTask.ps1`: регистрирует задачу Планировщика Windows, которая автоматически запускает скрипт автоматического резервного копирования PostgreSQL при старте компьютера.
- `HLA_Postgres_RemoteToLocal_Copy.ps1`: каждый час по умолчанию обновляет локальную базу PostgreSQL из удалённой базы PostgreSQL через `pg_dump` и `pg_restore`.
- `Install-HLA-PostgresRemoteCopyTask.ps1`: регистрирует задачу Планировщика Windows, которая автоматически запускает скрипт обновления локальной базы PostgreSQL при старте компьютера.
- `Update\HLA_ProgramFiles_RemoteUpdate.ps1`: выполняет только ручные проходы `ListOnly`/`RunOnce` по Viewer-ПК с промежуточным каталогом, проверкой SHA-256, активацией и откатом; полная инструкция находится в [`Update\README.md`](Update/README.md).

## Сборочные комплекты и ручное обновление Viewer

В `requirements.txt` остаются две команды-шаблона Nuitka:

- исходная команда GUI; её повторно запускают для требуемых вариантов приложения, задаваемых при сборке, не создавая отдельную инфраструктуру профилей сборки;
- отдельная команда без пользовательского интерфейса для `hla_file_base_writer_service.py`, создающая самостоятельную папку `HLA_FileBase_Writer` с `HLA_FileBase_Writer.exe`.

Эти команды выполняет Лицензиар при подготовке Официальной сборки. Получатель устанавливает только непосредственно переданный Лицензиаром выпуск с ролью, компонентами и идентификатором, указанными в его адресном разрешении; самостоятельная сборка получателем не является Официальной сборкой.

Автономный комплект — вся выходная папка, а не один `.exe`. Сначала выполняется команда GUI, затем команда Writer: повторный запуск GUI с `--remove-output` удалит вложенную папку Writer. Результат Writer намеренно расположен внутри выходной папки GUI; это часть комбинированного комплекта для узла Writer EFS, но не комплекта Viewer. Writer устанавливается и обновляется отдельно и никогда не распространяется средством обновления Viewer.

Каждый Лицензированный компьютер должен иметь самостоятельное адресное разрешение согласно `LICENSE.txt`. GUI и Writer на одном ПК могут составлять один экземпляр, только если оба компонента прямо перечислены в разрешении; при установке на разных ПК каждому требуется отдельное разрешение. Отдельный узел резервного копирования, зеркалирования, публикации или синхронизации БД, файловой базы, документов либо иных пользовательских данных также требует собственного разрешения независимо от ручного либо автоматического запуска сценария. Только временное техническое копирование файлов программы при установке или обновлении и разовый запуск поставленного сценария для ремонта либо диагностики уже разрешённого экземпляра не создают отдельного экземпляра. Развёртывание одной и той же сборки на нескольких Viewer-ПК требует самостоятельного адресного разрешения для каждого ПК; одно разрешение нельзя применить к списку устройств. Вместе с любой передаваемой полной папкой сохраняют корневые `LICENSE.txt`, `COPYRIGHT.txt`, `THIRD_PARTY_LICENSES.txt` и `licenses`; одну папку Writer без сопровождающих её файлов лицензий не передают.

Для комплекта Viewer администратор копирует полную папку правильной сборки GUI и удаляет из этой копии корневые `Scripts` и `HLA_FileBase_Writer`. Средство обновления зеркалирует это окончательное дерево целиком в `C:\Program Files\HLA_Laboratory_System` только на Viewer-ПК. ПК с правом записи, узел Writer `HLA-FB` и сервер публикации `HLA-VIEW` не являются его целями; имена приведены как административная схема и не зашиты в средство обновления.

Средство обновления проверяет безопасность и стабильность копирования, но намеренно не определяет заданный при сборке режим, роль компьютера, происхождение выпуска и совместимость БД. За правильную сборку, источник и список целей отвечает администратор. Каноническое имя узла DNS и IP используются только для запрета совпадения источника с целью, в том числе через иной псевдоним, и повторного указания одного физического целевого ПК; доказательством роли они не являются.

`Update\HLA_ProgramFiles_RemoteUpdate.ps1` не имеет установщика задачи, режима наблюдения, фоновых повторных попыток, файлов состояния или постоянных журналов. Рабочий каталог назначения зафиксирован как точный `C:\Program Files\HLA_Laboratory_System`. Сначала администратор запускает `ListOnly` только для чтения, затем отдельный подтверждённый `RunOnce`; одновременно во всём парке выполняется только один `RunOnce`. Подробный порядок, использование предыдущего каталога для отката и ограничения приведены в [`Update\README.md`](Update/README.md).

### Граница установки и обновления Laboratory

Средство обновления Viewer намеренно запрещено применять к сборкам `ENABLE_LABORATORY_ACTIONS=True`, серверу авторитетного корня, серверу физического зеркала и узлам автоматизации PostgreSQL. В репозитории нет автоматического средства удалённого обновления Laboratory: чистая установка и замена автономной папки Laboratory выполняются утверждённым средством развёртывания площадки после остановки приложения на целевом ПК. Нельзя копировать поверх работающего дерева отдельные `.exe` или модули.

Для Laboratory выпускается полная папка GUI с точными значениями всех трёх переключателей и профиля площадки. Серверные `Scripts` и `HLA_FileBase_Writer` считаются отдельными комплектами. После замены дерева `Scripts` заново регистрируют применимые задачи их установщиками, чтобы действие Планировщика, пути, учётная запись и защищённые параметры соответствовали новой версии, а затем выполняют проверки ниже.

`Install-HLA-FileBaseWriterService.ps1` является только установщиком на чистый узел и намеренно откажется работать поверх существующей службы или каталога состояния. Он не обновляет Writer. Обновление уже установленного Writer выполняется отдельной утверждённой процедурой обслуживания службы с заменой всей автономной папки Writer; изменение учётной записи, физического корня, режима или конфигурации требует чистого повторного развёртывания по [`Encryption\README.md`](Encryption/README.md), при котором защищённое состояние создаётся заново.

## Подготовка защищённой файловой базы

Оба режима защиты используют один строгий служебный контур управления схемы 4 в точной корневой `.hla_internal`: манифест с обязательным `deployment_mode`, общий физический `writer.lock` и долговечный журнал `transactions`. Постоянные исходные CSV находятся только в `<root>\<ОРГАН>\.source_files`. Для уже существующих каталогов администратор устанавливает атрибут `Hidden` при подготовке чистого корня; штатно создаваемые приложением каталоги получают его автоматически. Профиль `domain_network` требует описанные ниже доменные инварианты UNC/SMB и зеркала. Профиль `local_single_host` допускает только один локальный корень роли `authoritative` на фиксированном томе NTFS, запрещает UNC и зеркало и при EFS использует только локальный Writer без зависимости от `LanmanServer`. Автоматического переключения между профилями нет. Установка на боевых ПК только чистая: существующая `.hla_internal` или манифест другой схемы отклоняются.

`FILE_BASE_SERVICE_USER` — задаваемая при сборке учётная запись развёртывания физического корня внутри одной клиники; обычный пользователь не меняет её через интерфейс, пользовательские настройки или переменные окружения. `DEFAULT_LABORATORY` выбирает профиль клиники и связанную с ним служебную учётную запись; точное соответствие хранится в конфигурации сборки и здесь не дублируется. Все сборки с правом записи в один корень должны сопоставлять выбранную учётную запись с одним и тем же SID. Одинаковый UNC-псевдоним в разных клиниках относится к независимым физическим корням и манифестам. Полная подготовка ACL/EFS, сертификатов и Writer описана в [`Encryption\README.md`](Encryption/README.md).

`*.dump.gpg` может находиться непосредственно в корне файловой базы. GPG защищает содержимое резервной копии независимо от режима; публикация дополнительно проходит ту же блокировку `writer.lock`, барьер журнала и завершение ACL/EFS-защиты, что остальные управляемые записи.

### `domain_network`: авторитетный корень и Viewer-зеркало

- Физический источник: `D:\HLA_Laboratory_System` на сервере хранения.
- Канонический путь всех Laboratory-клиентов: `\\HLA-FB\HLA_Laboratory_System`.
- Канонический Viewer-путь: `\\HLA-VIEW\HLA_Laboratory_System`.
- Источник имеет роль `authoritative`, зеркало — `mirror`, разные `root_uuid` и точную связь `mirror_of_root_uuid`.
- Обратной синхронизации нет: частично обновлённое назначение никогда не становится источником; каждый повтор снова строится по авторитетному источнику, и только успешный проход сводит назначение к подтверждённому стабильному состоянию.

При ACL приложение и резервное копирование пишут напрямую по SMB под одним служебным SID, а зеркало обновляется под блокировкой `writer.lock` назначения со стабильной проверкой источника. При EFS приложения Laboratory передают изменения службе Writer на `HLA-FB`; локальная задача `SYSTEM` на `HLA-VIEW` просит уже работающий Writer роли `mirror` выполнить одно получение данных. Удалённое копирование зашифрованных объектов NTFS и прямая запись в назначение EFS не используются.

### Общая философия настройки

Длительно работающие эксплуатационные сценарии в этом каталоге настраиваются по одной схеме. Ручное средство обновления Viewer является отдельным исключением и описано в [`Update\README.md`](Update/README.md):

Учётные данные эксплуатационных сценариев задаются в рамках настройки самих сценариев и задач Планировщика Windows. Режим приложения `--passwords` предназначен для интерактивного приложения и не заменяет настройку сценариев из каталога `Scripts/`.

Повторный запуск установщика поддерживается при сохранении точного фактического SID субъекта безопасности и того же каталога служебного состояния: так можно менять параметры, пароли и режимы, которые не меняют владельца состояния, в том числе обычный или двухэтапный режим задач PostgreSQL. Смена логического `TaskUser`, фактического SID, полученного при разрешении имени, или служебной учётной записи требует утверждённого чистого удаления зарегистрированной задачи и её служебного состояния с последующей установкой как на новом узле. Переключение профиля развёртывания и ACL↔EFS у зеркала файловой базы также требует чистой установки; само переключение параметра не преобразует защиту существующего корня. При чистой установке каталоги состояния и DPAPI-файлы создаются заново; вручную переносить, переименовывать или перепривязывать их запрещено. Универсальные команды удаления намеренно не приводятся: очистку выполняют по утверждённой для конкретного узла процедуре после резервного копирования необходимых материалов восстановления.

- для каждого сценария наблюдения есть основной длительно работающий скрипт и отдельный установщик задачи Планировщика Windows;
- для боевого ПК рекомендуется не править `.ps1` под каждую площадку, а передавать значения, зависящие от конкретной площадки, через параметры запуска;
- установщики принимают только известные типизированные параметры, а неизвестные параметры отклоняются механизмом привязки параметров PowerShell;
- установщик зеркала файловой базы принимает канонический `-Source`; в ACL-режиме также обязательны `-Destination` и точный `-TaskUser`, а в EFS-режиме обязательны `-RequireEfsProtection` и локальный `-WriterClientPath`, тогда как назначение известно конфигурации Writer;
- установщик зеркала Word-заключений принимает обязательные `-Source`, `-Destination` и соответствующие типизированные параметры;
- чистая установка сценария наблюдения создаёт защищённые каталоги журналов и регистрирует одну задачу; только EFS-зеркализация файловой базы выполняет получение данных под управлением Writer, тогда как резервное копирование EFS использует отдельную типизированную публикацию `BACKUP`;
- `-RunOnce` и `-ListOnly` существуют только у основных сценариев и не входят в действие постоянно работающей задачи;
- основные скрипты зеркалирования файловой базы, резервного копирования PostgreSQL и инициализатор должны распространяться вместе с `Encryption\HLA_FileBase_Encryption_Common.psm1`; копирование одного `.ps1` без общего модуля является неполной установкой;
- задача Планировщика создаётся одна на весь компьютер и работает под одной постоянной учётной записью;
- `whoami` допустим только там, где текущая учётная запись намеренно является фактическим субъектом безопасности задачи и её SID дополнительно сверяется с зарегистрированным субъектом. Для зеркала файловой базы и резервного копирования PostgreSQL явно задаётся точный логический `FILE_BASE_SERVICE_USER`; установщик резервного копирования сопоставляет его с фактической учётной записью согласно топологии, а EFS-зеркало `domain_network` запускается под `SYSTEM`;
- сценарии разделены по назначению: файловая база публикуется из канонического UNC-корня роли `authoritative` в отдельный корень роли `mirror`, папка Word-заключений может зеркалироваться отдельно, а `.dump.gpg` публикуется в файловую базу через тот же служебный контур Writer и затем входит в зеркало Viewer.
- сетевые папки назначения для разных `robocopy /MIR` задач не должны пересекаться, если только это не один и тот же набор файлов с одинаковой относительной структурой. Иначе одна задача может удалить файлы другой как лишние для своего источника;
- копирование удалённой PostgreSQL в локальную PostgreSQL является отдельным сценарием: оно не создаёт файл резервной копии, а обновляет локальную базу через временную базу и последующую замену имени.

### Важные предупреждения

- Скрипт использует `robocopy /MIR`. Это режим зеркализации, а не обычного копирования.
- Для файловой базы используйте только канонический источник `\\HLA-FB\HLA_Laboratory_System`. Назначение ACL передаётся явно; назначение EFS не передаётся, поскольку Writer на `HLA-VIEW` привязан к локальному физическому корню роли `mirror`. Для зеркала Word-заключений `Source` и `Destination` задаются явно.
- Все объекты, существующие только в назначении и отсутствующие в источнике, будут удаляться из зеркала, кроме собственной точной корневой `.hla_internal` назначения.
- Сетевую папку назначения нужно использовать только как зеркало. Нельзя вручную хранить в ней отдельные рабочие файлы.
- Корни локальных дисков запрещены всегда. Корень общего ресурса SMB вида `\\СЕРВЕР\ШАРА` по умолчанию также запрещён и разрешается только явным параметром `-AllowShareRootDestination`. Этот параметр допустим, только если весь общий ресурс выделен исключительно под одно зеркало: `robocopy /MIR` может удалить из его корня любые объекты, которых нет в локальном источнике.
- Проверка источника и назначения выполняется до запуска наблюдателя, синхронизации и любого изменения назначения. При ошибке пути `robocopy /MIR` и публикация Writer не запускаются.
- Сценарий зеркализации Word-заключений зеркалирует файлы как есть. Он не преобразует `.doc` / `.docx` в PDF и не заменяет логику импорта в самом приложении.
- ACL-путь использует поддерживаемые локальной системой параметры `robocopy`, но `/MIR`, `/XJ`, точный перечень с учётом регистра, проверка метаданных и хешей и барьер журнала не ослабляются. Смягчение сравнения времени и копирование исходного зашифрованного потока EFS (`/EFSRAW`) не используются.
- Оба пути требуют строгие манифесты схемы 4 с `deployment_mode=domain_network`: источник=`authoritative`, назначение=`mirror`, разные UUID, правильный `mirror_of_root_uuid`, одинаковые режим защиты и служебный SID. Любой сценарий или задача зеркалирования файловой базы явно отклоняет `local_single_host`. Политика чтения независима: зеркало применяет собственные `reader_sids` и, при EFS, собственный набор получателей, а не копирует их из источника.
- В EFS профиль службы Writer на `HLA-VIEW` должен содержать закрытый ключ служебного сертификата источника (обычно тот же служебный PFX импортируется на оба узла Writer). Совпадение служебного SID само по себе не даёт возможности расшифровать источник.
- Из публикации исключается только точная корневая `.hla_internal` источника и назначения. Она никогда не копируется. Вложенные одноимённые пользовательские объекты являются данными.
- Каталоги `<ОРГАН>\.source_files` входят в публикацию. Обязательные параметры `robocopy /COPY:DAT /DCOPY:DAT /IT` переносят их атрибут `Hidden`; имя с точкой не является условием исключения.
- При смене физического корня либо канонического UNC задача регистрируется заново; локальный `D:` не записывается в конфигурацию GUI.
- Любое изменение локального пути папки с Word-заключениями или её сетевого зеркала требует синхронного обновления параметров `$Source` и `$Destination` в параметрах запуска соответствующей задачи.
- Если основной скрипт установлен не по пути по умолчанию, нужно также передать корректный `-SyncScriptPath` при регистрации соответствующей задачи.

## Зеркализация файловой базы

Ниже приведён порядок публикации из `\\HLA-FB\HLA_Laboratory_System` в `\\HLA-VIEW\HLA_Laboratory_System`. Оба физических корня должны быть независимо инициализированы до первой публикации.

### Предварительные условия

- Оба пути доступны только по SMB 3.x с обязательным шифрованием и настроенной политикой Hardened UNC Paths. Для клиента Laboratory EFS обязательны обе точные записи `\\HLA-FB\HLA_Laboratory_System` и `\\HLA-FB\IPC$`; остальные конечные точки перечислены в [`Encryption\README.md`](Encryption/README.md).
- Манифест источника имеет роль `authoritative`; манифест назначения — `mirror` и точную ссылку на UUID источника.
- Ни один корень или потомок не является точкой повторной обработки; `.hla_internal\transactions` обоих корней не содержит незавершённую операцию.
- ACL: задача работает под точной учётной записью `FILE_BASE_SERVICE_USER`, которая читает источник и пишет в назначение; весь общий ресурс SMB назначения выделен только под зеркало.
- EFS: Writer на `HLA-VIEW` установлен и запущен под точной учётной записью `FILE_BASE_SERVICE_USER`; задача запускается локально там под `SYSTEM` и не хранит второй пароль службы.

#### ACL: зарегистрировать задачу

Откройте повышенный Windows PowerShell 5.1 от имени администратора. Установщик изменяет защищённый каталог состояния и определение задачи; запускать этот блок под `TaskUser` не нужно.

```powershell
$ScriptDir = 'C:\Program Files\HLA_Laboratory_System\Scripts'
$Source = '\\HLA-FB\HLA_Laboratory_System'
$Destination = '\\HLA-VIEW\HLA_Laboratory_System'
$TaskUser = '<ДОМЕН\СЛУЖЕБНАЯ_УЧЁТНАЯ_ЗАПИСЬ>'

if (@($TaskUser) -match '<[^<>]+>') {
    throw 'Замените значения в угловых скобках перед запуском.'
}

& "$ScriptDir\Install-HLA-FileBaseMirrorTask.ps1" `
    -DeploymentMode domain_network `
    -TaskUser $TaskUser `
    -Source $Source `
    -Destination $Destination `
    -AllowShareRootDestination
```

Установщик проверяет доменную форму `TaskUser`, создаёт защищённый `C:\ProgramData\HLA_Laboratory_System\HLA_FileBase_Mirror\Logs`, запрашивает пароль точной служебной учётной записи и регистрирует задачу. Строгая сверка роли, UUID и режима обоих манифестов, их связи и SID выполняется `ListOnly` и каждым рабочим проходом до первой записи. Для корня выделенного общего ресурса SMB требуется явный `-AllowShareRootDestination`; не используйте его для общего ресурса с посторонними данными.

#### ACL: выполнить `ListOnly` и первый `RunOnce`

После успешной регистрации закройте повышенную административную сессию. Откройте отдельный Windows PowerShell 5.1 именно под зарегистрированным `TaskUser`, например утверждённым на площадке способом через `runas.exe`, и выполните весь блок ниже. Он сверяет SID текущего пользователя с субъектом безопасности задачи и повторяет её точные постоянные аргументы, поэтому нестандартные интервалы и параметры `robocopy` не теряются.

```powershell
$TaskName = 'HLA FileBase Local To Network Mirror'
$ExpectedPowerShell = "$env:SystemRoot\System32\WindowsPowerShell\v1.0\powershell.exe"
$ExpectedScript = 'C:\Program Files\HLA_Laboratory_System\Scripts\HLA_FileBase_LocalToNetwork_Mirror.ps1'
$Task = Get-ScheduledTask -TaskPath '\' -TaskName $TaskName -ErrorAction Stop
$Actions = @($Task.Actions)

if ($Actions.Count -ne 1) {
    throw 'У задачи ожидается ровно одно действие.'
}
$TaskAccount = New-Object System.Security.Principal.NTAccount `
    -ArgumentList ([string]$Task.Principal.UserId)
$TaskSid = $TaskAccount.Translate([System.Security.Principal.SecurityIdentifier]).Value
$CurrentSid = [System.Security.Principal.WindowsIdentity]::GetCurrent().User.Value
if ($TaskSid -cne $CurrentSid) {
    throw "Эту проверку нужно выполнять под точным TaskUser. SID задачи: $TaskSid; текущий SID: $CurrentSid"
}

$Action = $Actions[0]
if (-not [string]::Equals(
    [System.IO.Path]::GetFullPath([string]$Action.Execute),
    [System.IO.Path]::GetFullPath($ExpectedPowerShell),
    [System.StringComparison]::OrdinalIgnoreCase
)) {
    throw 'Задача запускает неожиданный исполняемый файл.'
}

$Arguments = [string]$Action.Arguments
$StablePrefix = '-NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden '
$ExpectedPrefix = $StablePrefix + "-File `"$ExpectedScript`" "
if (-not $Arguments.StartsWith($ExpectedPrefix, [System.StringComparison]::Ordinal)) {
    throw 'Действие задачи не имеет ожидаемый безопасный префикс и основной скрипт.'
}
foreach ($Match in [regex]::Matches(
    $Arguments,
    '(?i)(?:^|\s)(?:--?|/)(?<Name>[A-Za-z][A-Za-z0-9]*)(?=$|[\s:=])'
)) {
    $Name = $Match.Groups['Name'].Value
    if ('ListOnly'.StartsWith($Name, [System.StringComparison]::OrdinalIgnoreCase) -or
        'RunOnce'.StartsWith($Name, [System.StringComparison]::OrdinalIgnoreCase)) {
        throw "В постоянном действии задачи найден одноразовый параметр: $($Match.Value.Trim())"
    }
}
$InteractiveArguments = '-NoProfile -ExecutionPolicy Bypass ' +
    $Arguments.Substring($StablePrefix.Length)

$ListOnlyProcess = Start-Process -FilePath $ExpectedPowerShell `
    -ArgumentList "$InteractiveArguments -ListOnly" `
    -NoNewWindow -Wait -PassThru
if ($ListOnlyProcess.ExitCode -ne 0) {
    throw "ListOnly завершился с ошибкой: $($ListOnlyProcess.ExitCode)"
}
if ((Read-Host 'После проверки ListOnly для публикации зеркала введите MIRROR') -cne 'MIRROR') {
    throw 'Операция отменена.'
}
$RunOnceProcess = Start-Process -FilePath $ExpectedPowerShell `
    -ArgumentList "$InteractiveArguments -RunOnce" `
    -NoNewWindow -Wait -PassThru
if ($RunOnceProcess.ExitCode -ne 0) {
    throw "RunOnce завершился с ошибкой: $($RunOnceProcess.ExitCode)"
}
```

`ListOnly` не создаёт файлы и не обновляет журнал. Повышение прав обычного администратора не заменяет общий служебный SID.

ACL-проход удерживает `writer.lock` назначения, проверяет всё хранилище транзакций, подтверждает стабильность источника до и после копирования, точно устраняет различия в регистре имён путей, сверяет метаданные и содержимое и принимает результат только после конечной проверки обоих корней.

#### EFS: зарегистрировать локальную задачу на `HLA-VIEW`

Откройте повышенный Windows PowerShell 5.1 на сервере физического зеркала. Это серверный узел `HLA-VIEW`, а не Viewer-ПК с GUI-сборкой.

```powershell
$ScriptDir = 'C:\Program Files\HLA_Laboratory_System\Scripts'
$Source = '\\HLA-FB\HLA_Laboratory_System'
$Writer = 'C:\Program Files\HLA_Laboratory_System\HLA_FileBase_Writer\HLA_FileBase_Writer.exe'

& "$ScriptDir\Install-HLA-FileBaseMirrorTask.ps1" `
    -DeploymentMode domain_network `
    -Source $Source `
    -WriterClientPath $Writer `
    -RequireEfsProtection
```

Установщик требует локальный уже работающий Writer роли `mirror` и регистрирует задачу под `SYSTEM`. `Destination` и `TaskUser` в EFS-ветке не передаются. `ListOnly` для EFS намеренно отсутствует: только локальный Writer способен доказать успешное завершение EFS-защиты назначения.

Не запускайте основной скрипт напрямую из административной сессии: её SID не равен `SYSTEM`. Первое получение данных и дальнейший наблюдатель запускаются только зарегистрированной задачей:

```powershell
Start-ScheduledTask -TaskPath '\' -TaskName 'HLA FileBase Local To Network Mirror'
Start-Sleep -Seconds 3
$Task = Get-ScheduledTask -TaskPath '\' -TaskName 'HLA FileBase Local To Network Mirror'
if ([string]$Task.Principal.UserId -notin @('SYSTEM', 'NT AUTHORITY\SYSTEM')) {
    throw 'Задача EFS-зеркала зарегистрирована не под SYSTEM.'
}
$Task
Get-Content 'C:\ProgramData\HLA_Laboratory_System\HLA_FileBase_Mirror\Logs\watcher.log' -Tail 100
```

Тонкий локальный клиент не открывает серверную часть файловой базы и не хранит пароль. Он отправляет одну команду обслуживания уже работающей службе Writer, зарегистрированной в SCM; Writer локально получает данные, устанавливает физическую блокировку, проверяет барьер журнала, завершает EFS-защиту и выполняет итоговую проверку.

#### Запустить и проверить задачу

```powershell
Start-ScheduledTask -TaskName 'HLA FileBase Local To Network Mirror'
Get-ScheduledTask -TaskName 'HLA FileBase Local To Network Mirror'
Get-ScheduledTaskInfo -TaskName 'HLA FileBase Local To Network Mirror'
Get-Content 'C:\ProgramData\HLA_Laboratory_System\HLA_FileBase_Mirror\Logs\watcher.log' -Tail 100
```

Проверьте ожидаемую учётную запись (`FILE_BASE_SERVICE_USER` для ACL, `SYSTEM` для EFS), отсутствие немедленного завершения и успешную конечную проверку.

### Эксплуатационные примечания

- ACL использует `robocopy /MIR`: объекты, отсутствующие в источнике, удаляются из назначения. EFS делает эквивалентное сведение через локальный Writer.
- `/FFT` не применяется; точные имена с учётом регистра, типы, размеры, SHA-256 и поддерживаемые метаданные должны совпасть.
- Точки повторной обработки в корнях или деревьях блокируют хеширование и синхронизацию; `/XJ` обязателен.
- Точная корневая `.hla_internal` всегда служебная и никогда не зеркалируется; назначение сохраняет собственную. Вложенные одноимённые объекты зеркалируются.
- Наблюдатель реагирует на события, выполняет контрольный проход через `FullResyncMinutes` и повторяет неудавшиеся попытки через `RetryFailedSeconds`.
- `FullResyncMinutes=0` отключает только контрольный проход.
- Второй экземпляр на одном компьютере не запускается.
- Канонические файлы резервных копий `.dump.gpg` в корне входят в зеркало; закрытая промежуточная область находится только в `.hla_internal\transactions` и публикацией не переносится.
- Между парой обязаны совпасть режим и служебный SID, а роли и UUID-связь должны быть согласованы; физические идентичности корней обязаны различаться. У каждого корня фактические субъекты ACL и получатели EFS обязаны совпадать с его собственным манифестом; политики чтения источника и назначения между собой не сравниваются. Непустое или недействительное хранилище транзакций любого корня блокирует публикацию.

### Когда обновлять параметры

При неизменных SID и режиме повторно запустите установщик для изменения `Source`/`Destination`, пути к Writer, интервалов или параметров `robocopy` в ACL-режиме. Смена служебной учётной записи, ACL/EFS-режима или роли узла требует чистого удаления и повторной установки по общему правилу выше. Смена получателей EFS также требует новой чистой подготовки корней и контролируемого переключения; метаданные существующего дерева на месте не изменяются.

### Краткий контрольный список

- правильный режим только с ACL или с EFS выбран явно;
- источник и назначение физически независимы и не являются точками повторной обработки;
- назначение выделено только под это зеркало;
- состояние задачи создано установщиком;
- для ACL `ListOnly` и первый `RunOnce` выполнены под точным `TaskUser`, завершили сверку и проверку SHA-256;
- для EFS задача запущена под `SYSTEM`, первое получение данных Writer завершило итоговую EFS-проверку, а прямой административный `RunOnce` не использовался;
- задача запущена под правильной учётной записью для выбранной ветки;
- изменения появляются в зеркале после периода ожидания;
- отсутствующая в источнике тестовая копия удаляется из назначения ожидаемым `/MIR`.

## Зеркализация Word-заключений

Зеркало Word-заключений не связано с `ENABLE_FILE_BASE_ENCRYPTION`: оно копирует `.doc`/`.docx` и другие файлы как есть и не использует манифест EFS-защиты.

### Предварительные условия

- Локальный `-Source` и сетевой `-Destination` задаются явно.
- Назначение выделено под одно зеркало; разные `/MIR`-задачи не используют пересекающиеся корни.
- Учётная запись задачи читает источник и пишет в назначение.
- Для корня отдельного общего ресурса SMB осознанно используется `-AllowShareRootDestination`.

#### 1. Зарегистрировать задачу

```powershell
$ScriptDir = 'C:\Program Files\HLA_Laboratory_System\Scripts'
$Source = '<ПОЛНЫЙ_ПУТЬ_К_ПАПКЕ_С_WORD_ЗАКЛЮЧЕНИЯМИ>'
$Destination = '<UNC_ПУТЬ_К_ЗЕРКАЛУ_WORD_ЗАКЛЮЧЕНИЙ>'
```

Установщик также принимает типизированные `-UseCompression`, `-AllowShareRootDestination`, интервалы и параметры `robocopy`. Он создаёт защищённый каталог `C:\ProgramData\HLA_Laboratory_System\HLA_WordConclusions_Mirror\Logs` и регистрирует задачу с `Bypass`.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass `
```

### Корень выделенного общего ресурса SMB

Если `\\СЕРВЕР\ПАПКА_С_WORD_ЗАКЛЮЧЕНИЯМИ` является самим общим ресурсом SMB и целиком выделен под зеркало, добавьте `-AllowShareRootDestination` в установщик, `ListOnly` и `RunOnce`. ### Эксплуатационные примечания

- `/MIR` удаляет объекты, существующие только в назначении.
- `/FFT` не используется; реальный проход подтверждается SHA-256.
- `/XJ` обязателен, точки повторной обработки блокируются проверками.
- `Thumbs.db`, `ehthumbs.db`, `desktop.ini`, `$RECYCLE.BIN` и `System Volume Information` исключаются.
- Наблюдатель запускает синхронизацию после периода ожидания, периодически через `FullResyncMinutes` и после ошибок через `RetryFailedSeconds`.

- Сценарий не преобразует Word в PDF.
- Второй экземпляр не запускается.

### Когда обновлять параметры

При неизменном SID `TaskUser` повторно запустите установщик для изменения `Source`, `Destination`, интервалов, ограничения скорости, сжатия, разрешения использовать корень общего ресурса SMB или пути к скрипту. Смена `TaskUser` требует чистого удаления и повторной установки по общему правилу выше.

### Краткий контрольный список

- источник и назначение существуют и физически независимы;
- назначение выделено под это зеркало;
- задача и защищённое состояние журнала созданы установщиком;
- `ListOnly` проверен по консоли;
- `RunOnce` завершил SHA-256;
- задача запущена под ожидаемой учётной записью;
- создание, изменение и удаление тестового файла корректно отражаются в назначении.

## Автоматическое резервное копирование PostgreSQL

`HLA_Postgres_AutoBackup.ps1` отслеживает признаки записи в PostgreSQL и после периода тишины создаёт дамп в пользовательском формате, шифрует его GPG/AES256 и атомарно публикует скрытый `.dump.gpg`. В ACL-режиме публикация выполняется напрямую под общей блокировкой `writer.lock`; в EFS-режиме локальный интерфейс командной строки передаёт файл уже работающему Writer, не запускает вторую серверную часть и не получает закрытый ключ EFS. Пароли PostgreSQL и GPG не записываются в командную строку, XML задачи, постоянные переменные окружения или журнал. Пароль PostgreSQL задаётся как `PGPASSWORD` только в изолированной среде конкретной дочерней утилиты; среда процесса сценария не меняется, а дочерняя среда уничтожается после завершения. Пароль GPG передаётся через стандартный ввод.

### Как работает отслеживание

Для каждой настроенной БД сценарий получает признак записи по системной статистике. Изменение запускает период ожидания; после `DebounceSeconds` без новых изменений создаётся резервная копия. Независимо от событий полное резервное копирование выполняется через `FullBackupMinutes`. Ошибка проверки переводит цель в режим повторных попыток с сохранением доступности остальных целей: после восстановления связи создаётся резервная копия, даже если точную историю изменений установить нельзя.

### Важные предупреждения

- Обычный режим требует явных `-DbName` и `-BackupFile`; имя БД и путь по умолчанию отсутствуют.
- `-ImportDbStageMode` несовместим с `-DbName`, `-BackupFile` и `-BackupTarget` и требует `-BackupDirectory`.
- `-BackupTarget` принимает массив `DbName=FullBackupFilePath`; одна ошибочная цель не блокирует попытку остальных. `ListOnly`/`RunOnce` возвращают ненулевой код, если хотя бы одна цель недействительна или завершилась ошибкой.
- Каждая цель находится непосредственно в локальном физическом авторитетном корне, имеет каноническое имя `hla_postgres_[a-z0-9][a-z0-9_-]{0,63}.dump.gpg` и относится к одному `root_uuid`. В EFS-режиме обязателен `-RequireEfsProtection`.
- Парольная фраза GPG должна состоять только из печатных символов ASCII `U+0020`–`U+007E` и храниться в утверждённом хранилище восстановления. Для разделения рисков рекомендуется значение, отличное от пароля PostgreSQL, но их совпадение допустимо; без сохранённой точной фразы восстановление невозможно.
- Незашифрованный дамп существует только во время операции в защищённом `Work`; начало каждой реальной попытки резервного копирования очищает принадлежащие сценарию оставшиеся временные файлы. Если очистка не удалась, текущий проход больше не создаёт дамп ни для одной цели, а следующий проход сначала повторяет очистку. В корне файловой базы соседние `.tmp` и файлы отката не создаются.
- ACL-публикация использует закрытую промежуточную область только в `.hla_internal\transactions`, общий барьер журнала, канонический ACL файла и атомарную замену или перемещение. EFS-публикация использует только типизированную загрузку через Writer. В обоих путях подтверждаются длина, SHA-256 и `Hidden|Archive`; EFS дополнительно подтверждает манифест и получателей.
- `ListOnly` работает только для чтения: не очищает `Work`, не создаёт дамп и не пишет журнал.

### Предварительные условия

- `pg_dump.exe`, `psql.exe` и `gpg.exe` доступны автоматически либо их каталоги заданы типизированными параметрами.
- `TaskUser` всегда задаётся логическим `DOMAIN\User` из профиля сборки, а его SID обязан совпасть с `service_sid` манифеста. В `domain_network` разрешается только точная доменная запись. На ПК в рабочей группе или без присоединения к домену профиль `local_single_host` разрешает только включённого локального `COMPUTER\User` с тем же именем пользователя после прямой и обратной проверки типа SID `SidTypeUser`; другой домен и любая ошибка не запускают подстановку локальной записи.
- Парольная фраза GPG из печатных символов ASCII заранее сохранена в утверждённом хранилище восстановления.
- Для EFS полностью выполнена процедура [`Encryption\README.md`](Encryption/README.md), служба Writer запущена на этом физическом узле, а логический `TaskUser` совпадает с `FILE_BASE_SERVICE_USER` и сопоставляется с тем же фактическим SID, что и `service_sid` манифеста.

#### 3. Зарегистрировать задачу и секрет

Имя единственной задачи этой роли фиксировано: `HLA PostgreSQL Auto Backup`. Перед первой установкой блок ниже безопасно обнаружит отсутствие задачи. Перед повторной установкой он останавливает зарегистрированную задачу, ждёт завершения процесса и доказывает освобождение общего мьютекса; не продолжайте при ошибке проверки.

```powershell
$TaskName = 'HLA PostgreSQL Auto Backup'
$Task = Get-ScheduledTask -TaskPath '\' -TaskName $TaskName -ErrorAction SilentlyContinue
if ($null -ne $Task -and [string]$Task.State -in @('Running', 'Queued')) {
    Stop-ScheduledTask -TaskPath '\' -TaskName $TaskName -ErrorAction Stop
}
$Deadline = (Get-Date).AddSeconds(30)
do {
    $Task = Get-ScheduledTask -TaskPath '\' -TaskName $TaskName -ErrorAction SilentlyContinue
    if ($null -eq $Task -or [string]$Task.State -in @('Ready', 'Disabled')) { break }
    Start-Sleep -Milliseconds 250
} while ((Get-Date) -lt $Deadline)
if ($null -ne $Task -and [string]$Task.State -notin @('Ready', 'Disabled')) {
    throw 'Зарегистрированная задача не перешла в неактивное состояние.'
}

$Mutex = New-Object System.Threading.Mutex($false, 'Global\HLA_Postgres_AutoBackup')
$MutexOwned = $false
try {
    try { $MutexOwned = $Mutex.WaitOne(0) } catch [System.Threading.AbandonedMutexException] { $MutexOwned = $true }
    if (-not $MutexOwned) { throw 'Процесс зарегистрированной задачи ещё не завершён.' }
} finally {
    if ($MutexOwned) { $Mutex.ReleaseMutex() }
    $Mutex.Dispose()
}
```

Перед запуском установщика выберите парольную фразу GPG только из печатных символов ASCII `U+0020`–`U+007E` и сохраните её в утверждённом хранилище восстановления. Для разделения рисков рекомендуется не повторять пароль PostgreSQL, однако это не обязательное условие. Не вводите кириллицу, типографские кавычки и другие символы вне ASCII.

```powershell
$ScriptDir = 'C:\Program Files\HLA_Laboratory_System\Scripts'
$TaskUser = '<ДОМЕН\СЛУЖЕБНАЯ_УЧЁТНАЯ_ЗАПИСЬ>'
$DeploymentMode = '<domain_network ИЛИ local_single_host>'
$Protection = @{} # для EFS: @{ RequireEfsProtection = $true }

$ConfiguredValues = @($TaskUser, $DeploymentMode) + @($BackupParameters.Values | ForEach-Object { $_ })
if ($ConfiguredValues -match '<[^<>]+>') {
    throw 'Замените значения в угловых скобках перед запуском.'
}
if ($DeploymentMode -cnotin @('domain_network', 'local_single_host')) {
    throw 'Укажите точный профиль развёртывания файловой базы.'
}

$DbPassword = Read-Host 'Пароль PostgreSQL' -AsSecureString
$GpgPassword = Read-Host 'Парольная фраза GPG' -AsSecureString

try {
    & "$ScriptDir\Install-HLA-PostgresBackupTask.ps1" `
        -DeploymentMode $DeploymentMode `
        -TaskUser $TaskUser `
        -DbPassword $DbPassword `
        -GpgPassword $GpgPassword `
        @BackupParameters @Protection
} finally {
    if ($null -ne $DbPassword) { $DbPassword.Dispose() }
    if ($null -ne $GpgPassword) { $GpgPassword.Dispose() }
}
```

Если `-DbPassword` или `-GpgPassword` опущены, установщик безопасно запросит их интерактивно; для введённой парольной фразы GPG действует обязательное ограничение: только печатные символы ASCII. Затем он запросит пароль Windows для фактической учётной записи, с которой механизм разрешения имён сопоставил логический `TaskUser`: доменной записи в `domain_network` и на ПК точного настроенного домена либо локальной `COMPUTER\User` на ПК рабочей группы или без присоединения к домену в `local_single_host`. Значение `-TaskUser` при этом всегда остаётся логической учётной записью `DOMAIN\User`, заданной при сборке. Установщик создаст защищённые `Logs`, `Work`, `Secrets`, запишет новое поколение набора DPAPI, привязанного к фактическому SID, и зарегистрирует задачу под фактической учётной записью. На всё время ввода и регистрации установщик удерживает мьютекс роли и временно отключает зарегистрированную неактивную задачу. При ошибке до регистрации или после доказанного восстановления исходного определения задачи новое поколение удаляется. При неоднозначном итоге оно сохраняется отказобезопасно, обнаруженная задача остаётся отключённой до проверки администратором, а следующая успешная установка удаляет лишние поколения.

Запишите напечатанный путь вида:

`C:\ProgramData\HLA_Laboratory_System\HLA_PostgresBackup\Secrets\credentials_<GUID>.json`

В XML задачи хранится только этот путь. Сам файл защищён ACL и DPAPI, привязан к локальному компьютеру и SID задачи.

#### 4. Проверить первый запуск

Интерактивный блок `ListOnly`/`RunOnce` ниже допустим только в `domain_network`, если политика площадки разрешает интерактивный вход фактической доменной служебной записи. Закройте повышенную сессию установщика и откройте отдельный Windows PowerShell 5.1 именно под этой записью, например утверждённым администратором способом через `runas.exe '/user:<ДОМЕН\СЛУЖЕБНАЯ_УЧЁТНАЯ_ЗАПИСЬ>' powershell.exe`. Обычный повышенный администратор имеет другой SID и намеренно не проходит проверку манифеста цели. Блок сверяет SID с фактическим субъектом безопасности задачи, требует точный безопасный префикс действия PowerShell и повторно использует все зарегистрированные аргументы обычной, двухэтапной или пользовательской конфигурации.

```powershell
$TaskName = 'HLA PostgreSQL Auto Backup'
$ExpectedPowerShell = "$env:SystemRoot\System32\WindowsPowerShell\v1.0\powershell.exe"
$ExpectedScript = 'C:\Program Files\HLA_Laboratory_System\Scripts\HLA_Postgres_AutoBackup.ps1'
$Task = Get-ScheduledTask -TaskPath '\' -TaskName $TaskName -ErrorAction Stop
$Actions = @($Task.Actions)

if ($Actions.Count -ne 1) {
    throw 'У задачи ожидается ровно одно действие.'
}
$TaskAccount = New-Object System.Security.Principal.NTAccount `
    -ArgumentList ([string]$Task.Principal.UserId)
$TaskSid = $TaskAccount.Translate([System.Security.Principal.SecurityIdentifier]).Value
$CurrentSid = [System.Security.Principal.WindowsIdentity]::GetCurrent().User.Value
if ($TaskSid -cne $CurrentSid) {
    throw "Эту проверку нужно выполнять под точным TaskUser. SID задачи: $TaskSid; текущий SID: $CurrentSid"
}

$Action = $Actions[0]
if (-not [string]::Equals(
    [System.IO.Path]::GetFullPath([string]$Action.Execute),
    [System.IO.Path]::GetFullPath($ExpectedPowerShell),
    [System.StringComparison]::OrdinalIgnoreCase
)) {
    throw 'Задача запускает неожиданный исполняемый файл.'
}

$Arguments = [string]$Action.Arguments
$StablePrefix = '-NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden '
$ExpectedPrefix = $StablePrefix + "-File `"$ExpectedScript`" "
if (-not $Arguments.StartsWith($ExpectedPrefix, [System.StringComparison]::Ordinal)) {
    throw 'Действие задачи не имеет ожидаемый безопасный префикс и основной скрипт.'
}
foreach ($Match in [regex]::Matches(
    $Arguments,
    '(?i)(?:^|\s)(?:--?|/)(?<Name>[A-Za-z][A-Za-z0-9]*)(?=$|[\s:=])'
)) {
    $Name = $Match.Groups['Name'].Value
    if ('ListOnly'.StartsWith($Name, [System.StringComparison]::OrdinalIgnoreCase) -or
        'RunOnce'.StartsWith($Name, [System.StringComparison]::OrdinalIgnoreCase)) {
        throw "В постоянном действии задачи найден одноразовый параметр: $($Match.Value.Trim())"
    }
}
$InteractiveArguments = '-NoProfile -ExecutionPolicy Bypass ' +
    $Arguments.Substring($StablePrefix.Length)

$ListOnlyProcess = Start-Process -FilePath $ExpectedPowerShell `
    -ArgumentList "$InteractiveArguments -ListOnly" `
    -NoNewWindow -Wait -PassThru
if ($ListOnlyProcess.ExitCode -ne 0) {
    throw "ListOnly завершился с ошибкой: $($ListOnlyProcess.ExitCode)"
}
if ((Read-Host 'Для создания резервной копии введите BACKUP') -cne 'BACKUP') {
    throw 'Операция отменена.'
}
$RunOnceProcess = Start-Process -FilePath $ExpectedPowerShell `
    -ArgumentList "$InteractiveArguments -RunOnce" `
    -NoNewWindow -Wait -PassThru
if ($RunOnceProcess.ExitCode -ne 0) {
    throw "RunOnce завершился с ошибкой: $($RunOnceProcess.ExitCode)"
}
```

Для разрешённого интерактивного запуска `domain_network` проверьте вывод `ListOnly`: разрешённые пути, утилиты, соединение, признак записи и EFS-аудит. Свежий журнал от `ListOnly` не ожидается. Для нескольких целей `RunOnce` пробует каждую допустимую цель независимо, кроме общего отказобезопасного барьера `Work`: неудаляемый принадлежащий сценарию временный файл блокирует оставшиеся цели до следующего прохода; итоговый код ненулевой при любой ошибке. Проверьте `backup_watcher.log`, непустой `.dump.gpg` с атрибутами `Hidden|Archive`, проверку публикации SHA-256 и отсутствие принадлежащих сценарию `.tmp` в `Work`. Из объектов резервного копирования в корне остаётся только канонический итоговый `.dump.gpg`; временные файлы после успешного прохода отсутствуют. Обычные данные файловой базы не затрагиваются.

В `local_single_host` установщик намеренно назначает фактической учётной записи запреты интерактивного, удалённого и сетевого входа, поэтому `runas`, ручной `ListOnly` и ручной `RunOnce` не применяются. То же правило действует в `domain_network`, если интерактивный вход запрещён политикой площадки. Не ослабляйте запрещающие права и не запускайте блок от администратора: переходите к запуску зарегистрированной задачи и подтверждайте первое плановое резервное копирование по журналу, итоговому файлу и итоговой проверке публикации.

```powershell
Start-ScheduledTask -TaskName 'HLA PostgreSQL Auto Backup'
Get-ScheduledTask -TaskName 'HLA PostgreSQL Auto Backup'
```

Не объединяйте подготовку и проверочный запуск в один блок: установщик требует повышенного администратора, интерактивный `ListOnly`/`RunOnce` допустим только под субъектом безопасности с точным фактическим SID, а зарегистрированная задача сама использует этого субъекта. Для EFS добавьте `-RequireEfsProtection` в установщик; проверочные запуски повторно используют зарегистрированные аргументы задачи. Для двухэтапного режима при установке используйте `-ImportDbStageMode -BackupDirectory 'D:\HLA_Laboratory_System'` вместо `-DbName/-BackupFile`.

### Эксплуатационные примечания

- Установщик принимает типизированные `DbHost`, `DbPort`, `DbUser`, цель или цели, интервалы, `PgBinDir`, `GpgPath` и `RequireEfsProtection`.
- ACL-публикация удерживает физическую блокировку `writer.lock` и требует пустое и действительное хранилище транзакций. Интерфейс командной строки EFS открывает локальную сессию `BACKUP`; она допускает только загрузку, сигнал активности и закрытие, только точный служебный SID и только каноническое имя резервной копии непосредственно в корне.
- Код завершения Writer `2` или `3` считается отказом без принятой публикации. Код `4` принимается только если тот же процесс под служебной учётной записью независимо видит точные байты и SHA-256, атрибуты `Hidden|Archive`, политику ACL/EFS и неизменный манифест; иначе результат остаётся ошибкой для ручной проверки.
- Пароли в переменных окружения `HLA_APP_DB_PASSWORD` и `HLA_BACKUP_GPG_PASSWORD` намеренно запрещены.
- `TaskSecretPath` обязан указывать на точное версионное имя внутри защищённого `Secrets`.
- Операции резервного и удалённого копирования синхронизируются по имени каждой БД общим мьютексом.
- Обычная неудача одной цели не отменяет попытки остальных; общий барьер `Work` после неудаляемого временного файла намеренно блокирует оставшиеся цели до следующего прохода.
- При EFS готовый файл получает служебный сертификат и всех операторов из манифеста; дополнительные системные DRA остаются политикой Windows. Изменение манифеста во время публикации блокирует результат.
- Файл резервной копии получает точные поддерживаемые атрибуты `Hidden|Archive` и проверяется после атомарной замены.
- При неизменных логическом `TaskUser` и фактическом SID субъекта безопасности, полученном при сопоставлении имени, повторно запустите установщик после смены паролей, целей, путей либо обычного или двухэтапного профиля задачи. Параметр `RequireEfsProtection` можно изменить только для цели, уже заново подготовленной в соответствующем режиме защиты: установщик задачи не преобразует существующий ACL/EFS-корень. Смена логического `TaskUser` или фактического SID требует чистого удаления и повторной установки по общему правилу выше.
- Удаление заменяемого набора DPAPI означает, что сохранённую в нём парольную фразу больше нельзя извлечь для восстановления. Сначала подтвердите хранение точной парольной фразы GPG из печатных символов ASCII в утверждённом хранилище восстановления.

### Краткий контрольный список

- цели указаны явно и не дублируются;
- точная парольная фраза GPG из печатных символов ASCII сохранена в утверждённом хранилище восстановления;
- задача, ACL и набор DPAPI созданы установщиком;
- в `domain_network` при разрешённом интерактивном входе `ListOnly` проверил все цели без записи; в остальных случаях он намеренно пропущен;
- первая резервная копия создана интерактивным `RunOnce` только там, где он разрешён, либо зарегистрированной задачей под фактическим субъектом безопасности; результат подтверждён по коду и состоянию задачи, журналу и итоговой проверке публикации;
- `.dump.gpg` непуст, имеет точные `Hidden|Archive` и восстанавливается известным GPG-паролем;
- в EFS-режиме итоговая проверка публикации успешна;
- оставшиеся незашифрованные рабочие файлы отсутствуют после следующей реальной попытки резервного копирования;
- наблюдатель запущен и пишет `backup_watcher.log`.

## Восстановление PostgreSQL из зашифрованной резервной копии

Ниже приведён отдельный эксплуатационный порядок восстановления локальной PostgreSQL из выбранного файла резервной копии `.dump.gpg`.

Для стандартного режима с одной целью резервного копирования это обычно файл `hla_postgres_backup.dump.gpg`. Для `-ImportDbStageMode` используются файлы `hla_postgres_before.dump.gpg` и `hla_postgres_after.dump.gpg`; оператор выбирает нужный файл и восстанавливает его в соответствующую проверочную или рабочую БД.

Файл резервной копии зашифрован GPG и не может быть напрямую передан в `pg_restore.exe`. Сначала его нужно расшифровать во временный файл `.dump`, а затем восстановить этот `.dump` средствами PostgreSQL.

Резервная копия создаётся через `pg_dump --format=custom`, поэтому для восстановления используется `pg_restore.exe`, а не `psql.exe`.

### Важные предупреждения для восстановления PostgreSQL из резервной копии

- Рекомендуемый безопасный порядок — сначала восстановить резервную копию в отдельную базу, например `ИМЯ_БАЗЫ_ДЛЯ_ВОССТАНОВЛЕНИЯ`, и проверить результат.
- Не заменяйте рабочую базу сразу, пока не убедились, что файл резервной копии расшифровывается и успешно восстанавливается.
- Если планируется замена рабочей базы, перед восстановлением нужно закрыть приложение и остановить задачу `HLA PostgreSQL Auto Backup`.
- Для расшифровки нужна точная парольная фраза GPG, введённая как `-GpgPassword` при настройке задачи и сохранённая в утверждённом хранилище восстановления. Она должна состоять только из печатных символов ASCII `U+0020`–`U+007E`.
- Для команд PostgreSQL нужен актуальный пароль выбранного пользователя БД. Он может совпадать с парольной фразой GPG, хотя для разделения рисков рекомендуется использовать разные значения.
- В EFS-режиме одного повышения прав администратора недостаточно: учётная запись Windows, читающая `.dump.gpg`, должна иметь в своём `CurrentUser` закрытый ключ разрешённого EFS-сертификата оператора либо утверждённого DRA. Повышенную консоль открывайте под этой же учётной записью; не запускайте чтение под другим администратором.
- Команды расшифровки и готовый блок ниже выполняйте в предварительно открытой чистой сессии Windows PowerShell 5.1. Требование использовать только печатные символы ASCII исключает неоднозначное преобразование парольной фразы между кодировками, но не отменяет требование использовать штатную среду выполнения.
- После успешной проверки восстановленной базы незашифрованный файл `.dump` нужно удалить из служебного каталога восстановления.

### Предварительные условия для восстановления PostgreSQL из резервной копии

- нужный файл резервной копии существует, например `D:\HLA_Laboratory_System\hla_postgres_backup.dump.gpg`; для двухэтапного режима выберите `D:\HLA_Laboratory_System\hla_postgres_before.dump.gpg` или `D:\HLA_Laboratory_System\hla_postgres_after.dump.gpg`
- доступны `gpg.exe`, `psql.exe` и `pg_restore.exe`
- известна точная парольная фраза GPG из печатных символов ASCII, использованная при создании резервной копии
- известен актуальный пароль пользователя PostgreSQL
- известен пользователь PostgreSQL с правом создавать и удалять базы данных
- команды ниже выполняются из повышенного PowerShell под одной выбранной учётной записью; для EFS у неё должен быть доступен закрытый EFS-ключ

Если разрешённый сертификат ещё не установлен, импортируйте выданный администратором PFX в профиль той же учётной записи. Выполните блок только в рамках утверждённой процедуры работы с ключами:

```powershell
$PfxPath = '<ПУТЬ_К_УТВЕРЖДЁННОМУ_EFS_PFX>'
if (@($PfxPath) -match '<[^<>]+>') {
    throw 'Замените значения в угловых скобках перед запуском.'
}
if ((Read-Host 'Для импорта закрытого EFS-ключа введите IMPORT') -cne 'IMPORT') {
    throw 'Операция отменена.'
}

$PfxPassword = Read-Host 'Пароль PFX' -AsSecureString
try {
    Import-PfxCertificate -FilePath $PfxPath `
        -CertStoreLocation 'Cert:\CurrentUser\My' `
        -Password $PfxPassword -ErrorAction Stop
} finally {
    if ($null -ne $PfxPassword) { $PfxPassword.Dispose() }
}
```

PFX и его пароль не размещайте рядом с резервной копией. После подтверждения восстановления верните носитель ключа в хранилище восстановления по правилам площадки.

#### 1. Проверить файл резервной копии и служебные программы

Выполните:

```powershell
$PgBin = 'C:\Program Files\PostgreSQL\18\bin'
$Gpg = 'gpg.exe'
$BackupGpg = 'D:\HLA_Laboratory_System\hla_postgres_backup.dump.gpg'
$RestoreDir = 'C:\ProgramData\HLA_Laboratory_System\HLA_PostgresBackup\Restore'
$Dump = Join-Path $RestoreDir 'hla_postgres_backup.dump'
Import-Module 'C:\Program Files\HLA_Laboratory_System\Scripts\Common\HLA_Operations_Common.psm1' -Force -ErrorAction Stop

function Invoke-PostgresWithPassword {
    param([string]$ExecutablePath, [string[]]$Arguments, [string]$Password, [string]$FailureMessage)
    $Result = Invoke-HlaNativeProcessWithEnvironment -ExecutablePath $ExecutablePath -Arguments $Arguments -EnvironmentVariables @{ PGPASSWORD = $Password }
    if ($Result.ExitCode -ne 0) { throw "$FailureMessage Код: $($Result.ExitCode). $($Result.OutputText)" }
    $Result.StandardError | ForEach-Object { Write-Warning $_ }
    $Result.Output | Write-Output
}

$CurrentIdentity = [System.Security.Principal.WindowsIdentity]::GetCurrent().Name
Write-Host "Учётная запись Windows: $CurrentIdentity"
$EfsPrivateKeys = @(Get-ChildItem 'Cert:\CurrentUser\My' -ErrorAction Stop | Where-Object {
    $_.HasPrivateKey -and @(
        $_.EnhancedKeyUsageList | ForEach-Object { $_.ObjectId.Value }
    ) -match '^1\.3\.6\.1\.4\.1\.311\.10\.3\.4(?:\.1)?$'
})
$EfsPrivateKeys | Select-Object Subject, Thumbprint, NotAfter, HasPrivateKey

$BackupStream = $null
try {
    $BackupStream = [System.IO.File]::Open(
        $BackupGpg,
        [System.IO.FileMode]::Open,
        [System.IO.FileAccess]::Read,
        [System.IO.FileShare]::Read
    )
    if ($BackupStream.Length -le 0) {
        throw 'Файл резервной копии пуст.'
    }
} finally {
    if ($null -ne $BackupStream) { $BackupStream.Dispose() }
}

Get-Item -Force $BackupGpg -ErrorAction Stop
Get-Command $Gpg
& "$PgBin\psql.exe" --version
& "$PgBin\pg_restore.exe" --version
```

Если `gpg.exe` не находится через `PATH`, укажите полный путь, например:

```powershell
$Gpg = 'C:\Program Files\GnuPG\bin\gpg.exe'
```

#### 2. Расшифровать резервную копию во временный файл `.dump`

Введите ту же парольную фразу GPG из печатных символов ASCII, которая использовалась при настройке задачи. Символы вне ASCII здесь недопустимы даже при визуальном совпадении строки.

Выполните:

```powershell
$GpgPasswordSecure = Read-Host 'Парольная фраза GPG' -AsSecureString
$DumpReady = $false
$DecryptError = $null
$DumpCleanupError = $null

try {
    $GpgPassword = [System.Net.NetworkCredential]::new('', $GpgPasswordSecure).Password
    if ($GpgPassword -notmatch '^[\x20-\x7E]+$') {
        throw 'Парольная фраза GPG должна содержать только печатные символы ASCII с кодами 32–126.'
    }
    New-Item -ItemType Directory -Path $RestoreDir -Force -ErrorAction Stop | Out-Null

    if (Test-Path -LiteralPath $Dump) {
        Remove-Item -LiteralPath $Dump -Force -ErrorAction Stop
    }

    $GpgPassword | & $Gpg --batch --yes --pinentry-mode loopback --passphrase-fd 0 --output $Dump --decrypt $BackupGpg
    if ($LASTEXITCODE -ne 0) {
        throw 'GPG не смог расшифровать резервную копию. Проверьте пароль и используемую версию PowerShell.'
    }

    if (-not (Test-Path -LiteralPath $Dump -PathType Leaf)) {
        throw "GPG завершился без создания файла: $Dump"
    }

    & "$PgBin\pg_restore.exe" --list $Dump | Out-Null
    if ($LASTEXITCODE -ne 0) {
        throw "Расшифрованный файл не является корректным архивом pg_restore: $Dump"
    }

    Get-Item -Force $Dump -ErrorAction Stop
    $DumpReady = $true
} catch {
    $DecryptError = $_
} finally {
    if (-not $DumpReady -and (Test-Path -LiteralPath $Dump -PathType Leaf)) {
        try {
            Remove-Item -LiteralPath $Dump -Force -ErrorAction Stop
        } catch {
            $DumpCleanupError = $_
        }
    }
    $GpgPassword = $null
    if ($null -ne $GpgPasswordSecure) { $GpgPasswordSecure.Dispose() }
}
if ($null -ne $DumpCleanupError) {
    throw "Не удалось удалить неполный незашифрованный дамп. Ошибка операции: $(if ($null -ne $DecryptError) { $DecryptError.Exception.Message } else { 'нет' }). Ошибка очистки: $($DumpCleanupError.Exception.Message)"
}
if ($null -ne $DecryptError) { throw $DecryptError }
```

#### 3. Восстановить резервную копию в отдельную базу

В примерах ниже используется отдельная база `'<ИМЯ_БАЗЫ_ДЛЯ_ВОССТАНОВЛЕНИЯ>'`. Если такая база уже существует, она будет удалена и создана заново.

Выполните:

```powershell
$DbHost = 'localhost'
$DbPort = '5432'
$DbUser = 'postgres'
$DbName = '<ИМЯ_БАЗЫ_ДЛЯ_ВОССТАНОВЛЕНИЯ>'

if (@($DbName) -match '<[^<>]+>') {
    throw 'Замените значения в угловых скобках перед запуском.'
}
if ($DbName -notmatch '^[A-Za-z_][A-Za-z0-9_]{0,62}$' -or $DbUser -notmatch '^[A-Za-z_][A-Za-z0-9_]{0,62}$') {
    throw 'В этом готовом блоке имена базы и роли должны состоять только из латинских букв, цифр и знака подчёркивания.'
}
if (@('postgres', 'template0', 'template1') -contains $DbName) {
    throw 'Системную базу нельзя использовать как цель восстановления.'
}
if ((Read-Host "Для пересоздания проверочной базы «$DbName» введите её точное имя") -cne $DbName) {
    throw 'Операция отменена.'
}

$DbPasswordSecure = Read-Host 'Пароль PostgreSQL' -AsSecureString
try {
    $DbPassword = [System.Net.NetworkCredential]::new('', $DbPasswordSecure).Password
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\psql.exe" -Arguments @('-h', $DbHost, '-p', "$DbPort", '-U', $DbUser, '-d', 'postgres', '-v', 'ON_ERROR_STOP=1', '-c', "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = '$DbName' AND pid <> pg_backend_pid();") -Password $DbPassword -FailureMessage 'Не удалось завершить подключения к базе.'
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\psql.exe" -Arguments @('-h', $DbHost, '-p', "$DbPort", '-U', $DbUser, '-d', 'postgres', '-v', 'ON_ERROR_STOP=1', '-c', "DROP DATABASE IF EXISTS ""$DbName"";") -Password $DbPassword -FailureMessage 'Не удалось удалить базу.'
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\psql.exe" -Arguments @('-h', $DbHost, '-p', "$DbPort", '-U', $DbUser, '-d', 'postgres', '-v', 'ON_ERROR_STOP=1', '-c', "CREATE DATABASE ""$DbName"" OWNER ""$DbUser"";") -Password $DbPassword -FailureMessage 'Не удалось создать базу.'
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\pg_restore.exe" -Arguments @('--verbose', '--no-password', '--no-owner', '--no-acl', '--clean', '--if-exists', '--exit-on-error', '--single-transaction', '--host', $DbHost, '--port', "$DbPort", '--username', $DbUser, '--dbname', $DbName, $Dump) -Password $DbPassword -FailureMessage 'Восстановление базы завершилось с ошибкой.'
} finally {
    $DbPassword = $null
    if ($null -ne $DbPasswordSecure) { $DbPasswordSecure.Dispose() }
}
```

#### 4. Проверить восстановленную базу

Выполните:

```powershell
$DbPasswordSecure = Read-Host 'Пароль PostgreSQL' -AsSecureString
try {
    $DbPassword = [System.Net.NetworkCredential]::new('', $DbPasswordSecure).Password
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\psql.exe" -Arguments @('-h', $DbHost, '-p', "$DbPort", '-U', $DbUser, '-d', $DbName, '-v', 'ON_ERROR_STOP=1', '-c', '\dt') -Password $DbPassword -FailureMessage 'Проверка восстановленной базы завершилась с ошибкой.'
} finally {
    $DbPassword = $null
    if ($null -ne $DbPasswordSecure) { $DbPasswordSecure.Dispose() }
}
```

Ожидаемый результат:

- подключение к базе проходит без ошибок;
- список таблиц соответствует ожидаемой структуре приложения;
- приложение можно отдельно настроить на проверочную базу, если требуется функциональная проверка через интерфейс.

#### 5. При необходимости заменить рабочую базу

Этот шаг нужен только если после проверки принято решение восстановить данные поверх рабочей базы, точное имя которой затем задаётся в `$DbName`.

Сначала остановите приложение и задачу резервного копирования:

```powershell
$TaskName = 'HLA PostgreSQL Auto Backup'
$ExistingTask = Get-ScheduledTask -TaskPath '\' -ErrorAction Stop | Where-Object { $_.TaskName -eq $TaskName }
if ($null -ne $ExistingTask -and (@('Running', 'Queued') -contains [string]$ExistingTask.State)) {
    Stop-ScheduledTask -InputObject $ExistingTask -ErrorAction Stop
    $StopDeadline = (Get-Date).AddSeconds(30)
    do {
        Start-Sleep -Seconds 1
        $ExistingTask = Get-ScheduledTask -TaskPath '\' -ErrorAction Stop | Where-Object { $_.TaskName -eq $TaskName }
    } while ($null -ne $ExistingTask -and (@('Running', 'Queued') -contains [string]$ExistingTask.State) -and (Get-Date) -lt $StopDeadline)
    if ($null -ne $ExistingTask -and (@('Running', 'Queued') -contains [string]$ExistingTask.State)) { throw "Не удалось остановить задачу: $TaskName" }
}
```

Задайте имя рабочей базы:

```powershell
$DbName = '<ИМЯ_РАБОЧЕЙ_БАЗЫ>'

if (@($DbName) -match '<[^<>]+>') {
    throw 'Замените значения в угловых скобках перед запуском.'
}
```

Затем завершите активные подключения, пересоздайте рабочую базу и восстановите в неё тот же расшифрованный `.dump`:

```powershell
if ($DbName -notmatch '^[A-Za-z_][A-Za-z0-9_]{0,62}$' -or $DbUser -notmatch '^[A-Za-z_][A-Za-z0-9_]{0,62}$') {
    throw 'В этом готовом блоке имена базы и роли должны состоять только из латинских букв, цифр и знака подчёркивания.'

if (@('postgres', 'template0', 'template1') -contains $DbName) {

}
if ((Read-Host "Для пересоздания рабочей базы «$DbName» введите её точное имя") -cne $DbName) {
    throw 'Операция отменена.'
}

$DbPasswordSecure = Read-Host 'Пароль PostgreSQL' -AsSecureString
try {
    $DbPassword = [System.Net.NetworkCredential]::new('', $DbPasswordSecure).Password
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\psql.exe" -Arguments @('-h', $DbHost, '-p', "$DbPort", '-U', $DbUser, '-d', 'postgres', '-v', 'ON_ERROR_STOP=1', '-c', "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = '$DbName' AND pid <> pg_backend_pid();") -Password $DbPassword -FailureMessage 'Не удалось завершить подключения к рабочей базе.'
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\psql.exe" -Arguments @('-h', $DbHost, '-p', "$DbPort", '-U', $DbUser, '-d', 'postgres', '-v', 'ON_ERROR_STOP=1', '-c', "DROP DATABASE IF EXISTS ""$DbName"";") -Password $DbPassword -FailureMessage 'Не удалось удалить рабочую базу.'
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\psql.exe" -Arguments @('-h', $DbHost, '-p', "$DbPort", '-U', $DbUser, '-d', 'postgres', '-v', 'ON_ERROR_STOP=1', '-c', "CREATE DATABASE ""$DbName"" OWNER ""$DbUser"";") -Password $DbPassword -FailureMessage 'Не удалось создать рабочую базу.'
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\pg_restore.exe" -Arguments @('--verbose', '--no-password', '--no-owner', '--no-acl', '--clean', '--if-exists', '--exit-on-error', '--single-transaction', '--host', $DbHost, '--port', "$DbPort", '--username', $DbUser, '--dbname', $DbName, $Dump) -Password $DbPassword -FailureMessage 'Восстановление рабочей базы завершилось с ошибкой.'
} finally {

    if ($null -ne $DbPasswordSecure) { $DbPasswordSecure.Dispose() }
}
```

После замены рабочей базы запустите задачу резервного копирования снова:

```powershell
Start-ScheduledTask -TaskName "HLA PostgreSQL Auto Backup"
```

#### 6. Удалить незашифрованный файл `.dump`

После успешной проверки восстановленной базы удалите незашифрованный файл `.dump` из служебного каталога восстановления:

```powershell
if ([System.IO.Path]::GetFullPath($Dump) -ne [System.IO.Path]::GetFullPath((Join-Path $RestoreDir 'hla_postgres_backup.dump'))) {
    throw 'Путь к незашифрованному дампу отличается от ожидаемого служебного пути.'
}
Remove-Item -LiteralPath $Dump -Force -ErrorAction Stop
if (Test-Path -LiteralPath $Dump) { throw 'Незашифрованный дамп не был удалён.' }
```

### Готовый набор команд через `whoami`

Перед запуском блока ниже обязательно проверьте и при необходимости замените:

- `$PgBin = 'C:\Program Files\PostgreSQL\18\bin'` на фактический путь к PostgreSQL 18 `bin`;
- `$Gpg = 'gpg.exe'` на полный путь к `gpg.exe`, если Gpg4win не доступен через `PATH`;
- `$BackupGpg = 'D:\HLA_Laboratory_System\hla_postgres_backup.dump.gpg'` на фактический путь к зашифрованной резервной копии. Для двухэтапного режима это может быть `hla_postgres_before.dump.gpg` или `hla_postgres_after.dump.gpg`;
- `$DbName = '<ИМЯ_БАЗЫ_ДЛЯ_ВОССТАНОВЛЕНИЯ>'` на имя отдельной базы, в которую нужно восстановить резервную копию;
- `$DbUser = 'postgres'` на пользователя PostgreSQL с правом создавать и удалять базы данных;
- для EFS-корня текущая повышенная учётная запись и запускаемая из неё чистая сессия Windows PowerShell 5.1 должны использовать тот же профиль `CurrentUser` с разрешённым закрытым EFS-ключом, проверенным в шаге 1;
- парольная фраза GPG из печатных символов ASCII и пароль PostgreSQL будут запрошены без отображения ввода.

Команды ниже восстанавливают резервную копию в отдельную базу `'<ИМЯ_БАЗЫ_ДЛЯ_ВОССТАНОВЛЕНИЯ>'`. Не подставляйте имя рабочей базы в `$DbName`, если не выполнены действия из шага 5.

Если сейчас открыта PowerShell 7 или обычная интерактивная сессия PowerShell с загруженным профилем, для ручного восстановления рекомендуется сначала открыть чистую сессию Windows PowerShell 5.1:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass
```

Это рекомендуется для совместимости с эксплуатационными сценариями из каталога `Scripts`, рассчитанными на Windows PowerShell 5.1.

После этого выполните набор команд восстановления ниже уже в открывшейся чистой сессии Windows PowerShell 5.1.

Команды:

```powershell

$DbPort = '5432'
$DbUser = 'postgres'
$DbName = '<ИМЯ_БАЗЫ_ДЛЯ_ВОССТАНОВЛЕНИЯ>'
$RunUser = (whoami).Trim()
Import-Module 'C:\Program Files\HLA_Laboratory_System\Scripts\Common\HLA_Operations_Common.psm1' -Force -ErrorAction Stop

function Invoke-PostgresWithPassword {
    param([string]$ExecutablePath, [string[]]$Arguments, [string]$Password, [string]$FailureMessage)
    $Result = Invoke-HlaNativeProcessWithEnvironment -ExecutablePath $ExecutablePath -Arguments $Arguments -EnvironmentVariables @{ PGPASSWORD = $Password }
    if ($Result.ExitCode -ne 0) { throw "$FailureMessage Код: $($Result.ExitCode). $($Result.OutputText)" }
    $Result.StandardError | ForEach-Object { Write-Warning $_ }
    $Result.Output | Write-Output
}

if (@($BackupGpg, $DbName) -match '<[^<>]+>') {
    throw 'Замените значения в угловых скобках перед запуском.'
}
if ($DbName -notmatch '^[A-Za-z_][A-Za-z0-9_]{0,62}$' -or $DbUser -notmatch '^[A-Za-z_][A-Za-z0-9_]{0,62}$') {
    throw 'В этом готовом блоке имена базы и роли должны состоять только из латинских букв, цифр и знака подчёркивания.'
}
if (@('postgres', 'template0', 'template1') -contains $DbName) {
    throw 'Системную базу нельзя использовать как цель восстановления.'
}
if ([System.IO.Path]::GetFullPath($Dump) -ne [System.IO.Path]::GetFullPath((Join-Path $RestoreDir 'hla_postgres_backup.dump'))) {
    throw 'Путь к незашифрованному дампу отличается от ожидаемого служебного пути.'
}
if ((Read-Host "Для расшифровки резервной копии и пересоздания базы «$DbName» введите её точное имя") -cne $DbName) {
    throw 'Операция отменена.'
}

$GpgPasswordSecure = Read-Host 'Парольная фраза GPG' -AsSecureString
$DbPasswordSecure = Read-Host 'Пароль PostgreSQL' -AsSecureString
$RestoreError = $null
$DumpCleanupError = $null

try {
    $GpgPassword = [System.Net.NetworkCredential]::new('', $GpgPasswordSecure).Password
    $DbPassword = [System.Net.NetworkCredential]::new('', $DbPasswordSecure).Password
    if ($GpgPassword -notmatch '^[\x20-\x7E]+$') {
        throw 'Парольная фраза GPG должна содержать только печатные символы ASCII с кодами 32–126.'
    }

    $RunUser
    Get-Item -Force $BackupGpg -ErrorAction Stop
    Get-Command $Gpg -ErrorAction Stop

    & "$PgBin\psql.exe" --version
    if ($LASTEXITCODE -ne 0) { throw "psql недоступен. Код: $LASTEXITCODE" }

    & "$PgBin\pg_restore.exe" --version
    if ($LASTEXITCODE -ne 0) { throw "pg_restore недоступен. Код: $LASTEXITCODE" }

    New-Item -ItemType Directory -Path $RestoreDir -Force -ErrorAction Stop | Out-Null

    if (Test-Path -LiteralPath $Dump) {
        Remove-Item -LiteralPath $Dump -Force -ErrorAction Stop
    }

    $GpgPassword | & $Gpg --batch --yes --pinentry-mode loopback --passphrase-fd 0 --output $Dump --decrypt $BackupGpg
    if ($LASTEXITCODE -ne 0) { throw "GPG не смог расшифровать резервную копию. Код: $LASTEXITCODE" }

    if (-not (Test-Path -LiteralPath $Dump -PathType Leaf)) {
        throw "GPG завершился без создания файла: $Dump"
    }

    & "$PgBin\pg_restore.exe" --list $Dump | Out-Null
    if ($LASTEXITCODE -ne 0) { throw "Расшифрованный файл не является корректным архивом pg_restore: $Dump" }

    Get-Item -Force $Dump -ErrorAction Stop
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\psql.exe" -Arguments @('-h', $DbHost, '-p', "$DbPort", '-U', $DbUser, '-d', 'postgres', '-v', 'ON_ERROR_STOP=1', '-c', "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = '$DbName' AND pid <> pg_backend_pid();") -Password $DbPassword -FailureMessage 'Не удалось завершить подключения к базе.'
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\psql.exe" -Arguments @('-h', $DbHost, '-p', "$DbPort", '-U', $DbUser, '-d', 'postgres', '-v', 'ON_ERROR_STOP=1', '-c', "DROP DATABASE IF EXISTS ""$DbName"";") -Password $DbPassword -FailureMessage 'Не удалось удалить базу.'
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\psql.exe" -Arguments @('-h', $DbHost, '-p', "$DbPort", '-U', $DbUser, '-d', 'postgres', '-v', 'ON_ERROR_STOP=1', '-c', "CREATE DATABASE ""$DbName"" OWNER ""$DbUser"";") -Password $DbPassword -FailureMessage 'Не удалось создать базу.'
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\pg_restore.exe" -Arguments @('--verbose', '--no-password', '--no-owner', '--no-acl', '--clean', '--if-exists', '--exit-on-error', '--single-transaction', '--host', $DbHost, '--port', "$DbPort", '--username', $DbUser, '--dbname', $DbName, $Dump) -Password $DbPassword -FailureMessage 'Восстановление базы завершилось с ошибкой.'
    Invoke-PostgresWithPassword -ExecutablePath "$PgBin\psql.exe" -Arguments @('-h', $DbHost, '-p', "$DbPort", '-U', $DbUser, '-d', $DbName, '-v', 'ON_ERROR_STOP=1', '-c', '\dt') -Password $DbPassword -FailureMessage 'Проверка восстановленной базы завершилась с ошибкой.'
} catch {
    $RestoreError = $_
} finally {
    if (Test-Path -LiteralPath $Dump -PathType Leaf) {
        try {
            Remove-Item -LiteralPath $Dump -Force -ErrorAction Stop
        } catch {
            $DumpCleanupError = $_
        }
    }
    $GpgPassword = $null
    $DbPassword = $null
    if ($null -ne $GpgPasswordSecure) { $GpgPasswordSecure.Dispose() }
    if ($null -ne $DbPasswordSecure) { $DbPasswordSecure.Dispose() }
}
if ($null -ne $DumpCleanupError) {
    throw "Не удалось удалить незашифрованный дамп. Ошибка восстановления: $(if ($null -ne $RestoreError) { $RestoreError.Exception.Message } else { 'нет' }). Ошибка очистки: $($DumpCleanupError.Exception.Message)"
}
if ($null -ne $RestoreError) { throw $RestoreError }
}
```

- приложение закрыто, если планируется замена рабочей базы
- задача `HLA PostgreSQL Auto Backup` остановлена, если планируется замена рабочей базы
- нужный файл `.dump.gpg` существует
- `gpg.exe`, `psql.exe` и `pg_restore.exe` доступны
- точная парольная фраза GPG из печатных символов ASCII и актуальный пароль PostgreSQL известны
- сначала выполнено восстановление в отдельную базу
- восстановленная база проверена через `psql.exe` или приложение
- задача `HLA PostgreSQL Auto Backup` запущена снова, если она останавливалась

## Копирование удалённой PostgreSQL в локальную PostgreSQL

`HLA_Postgres_RemoteToLocal_Copy.ps1` периодически получает дамп удалённой БД в пользовательском формате, восстанавливает его во временную локальную БД, проверяет её и только затем заменяет локальную цель. В обычном режиме имена источника и цели задаются явно; `-ImportDbStageMode` обрабатывает пары `hla_db_before` и `hla_db_after`.

Пароли удалённого и локального PostgreSQL не записываются в командную строку, XML задачи или постоянные переменные окружения. Установщик сохраняет их в версионированном наборе учётных данных DPAPI, привязанном к компьютеру и защищённом ACL. Для каждого вызова утилиты PostgreSQL соответствующий пароль задаётся как `PGPASSWORD` только в изолированной дочерней среде; среда процесса сценария не меняется, а дочерняя среда уничтожается после завершения.

Это серверный сценарий автоматизации, а не часть дистрибутива Viewer. Полное дерево `Scripts` устанавливается на отдельный доверенный Windows-узел, который имеет сетевой доступ к исходной и целевой PostgreSQL и постоянно запускает задачу под одним `TaskUser`. По умолчанию целевая PostgreSQL находится на этом же узле (`LocalDbHost=localhost`); при отдельном сервере задайте `-LocalDbHost` явно. Не устанавливайте задачу и не возвращайте `Scripts` на Viewer-ПК.

### Важные предупреждения

- Локальная цель заменяется данными удалённой БД; не храните там уникальные локальные данные.
- При публикации завершаются активные подключения к локальной целевой БД.
- Двухэтапные пары выполняются последовательно и не являются общим снимком или транзакцией: первая может обновиться, даже если вторая завершилась ошибкой.
- Для локального подключения нужны права создавать, переименовывать, удалять БД и завершать подключения.
- Для удалённого подключения нужны `CONNECT` и чтение всех требуемых данных.
- Жизненный цикл целевых и служебных локальных БД (`CREATE`, `DROP`, `ALTER DATABASE`, переименование) единолично обслуживает эта задача на одном узле. Внешние администраторы, другие задания и второй узел не выполняют параллельный DDL: локальный мьютекс не защищает от другого компьютера и несогласованного администратора.
- Рабочий каталог фиксирован: `C:\ProgramData\HLA_Laboratory_System\HLA_PostgresRemoteCopy\Work`; переопределение отсутствует.
- Обычный проход удаляет незашифрованный дамп в `finally`. После аварийного завершения процесса начало каждого следующего изменяющего прохода безопасно удаляет только принадлежащие сценарию файлы строгого имени; если удалить такой файл нельзя, проход завершается до создания новых дампов.
- `-KeepDump` разрешён только вместе с ручным `-RunOnce`; запланированная задача этот флаг не принимает.
- `ListOnly` работает только для чтения: не создаёт и не очищает `Work` и не пишет журнал.
- Пароли в переменных окружения `HLA_REMOTE_DB_PASSWORD` и `HLA_APP_DB_PASSWORD` запрещены.

### Имена БД

Обычный режим требует все четыре значения:

- `-RemoteDbHost`
- `-RemoteDbUser`
- `-RemoteDbName`
- `-LocalDbName`

`-ImportDbStageMode` запрещает `-RemoteDbName` и `-LocalDbName` и создаёт точные пары:

- удалённая `hla_db_before` → локальная `hla_db_before`
- удалённая `hla_db_after` → локальная `hla_db_after`

Сценарий не берёт эти имена из `HLA_REMOTE_DB_NAME` или `HLA_APP_DB_NAME`.

### Настройка удалённого PostgreSQL

На удалённом сервере откройте интерактивный `psql.exe` с административными правами. Выполните только одну ветку ниже. Роль создаётся один раз; если утверждённая роль только для чтения уже существует, строку `CREATE ROLE` повторно не выполняйте.

Обычный режим для одной явно выбранной исходной БД:

```sql
CREATE ROLE hla_remote_reader LOGIN;
GRANT CONNECT ON DATABASE <ИМЯ_УДАЛЁННОЙ_БАЗЫ> TO hla_remote_reader;

\connect <ИМЯ_УДАЛЁННОЙ_БАЗЫ>
GRANT USAGE ON SCHEMA public TO hla_remote_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO hla_remote_reader;
GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO hla_remote_reader;
```

Двухэтапный режим для двух точных исходных БД:

```sql
CREATE ROLE hla_remote_reader LOGIN;
GRANT CONNECT ON DATABASE hla_db_before TO hla_remote_reader;
GRANT CONNECT ON DATABASE hla_db_after TO hla_remote_reader;

\connect hla_db_before
GRANT USAGE ON SCHEMA public TO hla_remote_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO hla_remote_reader;
GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO hla_remote_reader;

\connect hla_db_after
GRANT USAGE ON SCHEMA public TO hla_remote_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO hla_remote_reader;
GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO hla_remote_reader;
```

Не добавляйте эту роль в `pg_read_all_data`: она может открыть чтение других доступных БД кластера. Блоки предполагают, что прикладные объекты находятся только в `public`. Для других прикладных схем повторите три `GRANT` только в выбранных БД и только для требуемых схем. После создания новых таблиц или последовательностей повторите выдачу прав либо настройте от имени точного владельца объектов:

```sql
\connect <ИМЯ_РАЗРЕШЁННОЙ_БАЗЫ>
ALTER DEFAULT PRIVILEGES FOR ROLE <ВЛАДЕЛЕЦ_ОБЪЕКТОВ> IN SCHEMA public
    GRANT SELECT ON TABLES TO hla_remote_reader;
ALTER DEFAULT PRIVILEGES FOR ROLE <ВЛАДЕЛЕЦ_ОБЪЕКТОВ> IN SCHEMA public
    GRANT SELECT ON SEQUENCES TO hla_remote_reader;
```

Затем отдельно выполните в том же интерактивном `psql.exe` команду ниже. `\password` запросит новый пароль дважды без отображения и не сохранит его в этом файле или истории команд:

```text
\password hla_remote_reader
```

В `pg_hba.conf` не должно быть более широкого правила, разрешающего этой роли подключаться к другим БД. Для обычного режима добавьте одну строку и замените оба заполнителя:

```text
host    <ИМЯ_УДАЛЁННОЙ_БАЗЫ>    hla_remote_reader    <IP_УЗЛА_REMOTE_COPY>/32    scram-sha-256
```

Для двухэтапного режима добавьте две точные строки:

```text
host    hla_db_before    hla_remote_reader    <IP_УЗЛА_REMOTE_COPY>/32    scram-sha-256
host    hla_db_after     hla_remote_reader    <IP_УЗЛА_REMOTE_COPY>/32    scram-sha-256
```

После изменения конфигурации:

```sql
SELECT pg_reload_conf();
```

Также откройте TCP 5432 только для нужного адреса или сегмента и проверьте, что PostgreSQL слушает нужный интерфейс. Не выдавайте удалённой учётной записи чтения права записи или суперпользователя.

### Предварительные условия

- `pg_dump.exe`, `pg_restore.exe`, `psql.exe` доступны; версии совместимы с удалённым/локальным PostgreSQL.
- Удалённый межсетевой экран и `pg_hba.conf` настроены.
- Локальная служебная БД (по умолчанию `postgres`) отличается от локальной цели.
- `TaskUser` — точная постоянная учётная запись задачи на выделенном узле удалённого копирования; её SID используется для секрета DPAPI и состояния задачи. Администратор с другим SID не выполняет проверочные вызовы вместо неё.
- Пользователи приложения предупреждены о кратком разрыве соединений при публикации.

#### 1. Проверить сеть и утилиты

```powershell
$RemoteHost = '<АДРЕС_УДАЛЁННОГО_POSTGRESQL>'
if (@($RemoteHost) -match '<[^<>]+>') {
    throw 'Замените значения в угловых скобках перед запуском.'
```

#### 2. Зарегистрировать задачу и набор учётных данных

Первая установка выполняется сразу. Перед любым повторным запуском установщика, включая смену только пароля или интервала, остановите зарегистрированную задачу, дождитесь освобождения её процесса и убедитесь, что задача с существующими действием и секретом полностью восстановила каждый долговечный журнал. Установщик намеренно не останавливает активную задачу, не запускает заменяющую конфигурацию автоматически и не заменяет задачу при наличии журнала.

```powershell
$TaskName = 'HLA PostgreSQL Remote To Local Copy'
$WorkDir = 'C:\ProgramData\HLA_Laboratory_System\HLA_PostgresRemoteCopy\Work'
$Task = Get-ScheduledTask -TaskPath '\' -TaskName $TaskName -ErrorAction SilentlyContinue
if ($null -ne $Task -and [string]$Task.State -in @('Running', 'Queued')) {
    Stop-ScheduledTask -TaskPath '\' -TaskName $TaskName -ErrorAction Stop
}
$Deadline = (Get-Date).AddSeconds(30)
do {
    $Task = Get-ScheduledTask -TaskPath '\' -TaskName $TaskName -ErrorAction SilentlyContinue
    if ($null -eq $Task -or [string]$Task.State -in @('Ready', 'Disabled')) { break }
    Start-Sleep -Milliseconds 250
} while ((Get-Date) -lt $Deadline)
if ($null -ne $Task -and [string]$Task.State -notin @('Ready', 'Disabled')) {
    throw 'Зарегистрированная задача не перешла в неактивное состояние.'
}

$Mutex = New-Object System.Threading.Mutex($false, 'Global\HLA_Postgres_RemoteToLocal_Copy')
$MutexOwned = $false
try {
    try { $MutexOwned = $Mutex.WaitOne(0) } catch [System.Threading.AbandonedMutexException] { $MutexOwned = $true }
    if (-not $MutexOwned) { throw 'Процесс зарегистрированной задачи ещё не завершён.' }
} finally {
    if ($MutexOwned) { $Mutex.ReleaseMutex() }
    $Mutex.Dispose()
}

$PendingJournals = if (Test-Path -LiteralPath $WorkDir -PathType Container) {
    @(Get-ChildItem -LiteralPath $WorkDir -Filter 'hla_remote_copy_swap_*.json' -Force -ErrorAction Stop)
} else {
    @()
}
if ($PendingJournals.Count -ne 0) {
    $PendingJournals | Select-Object FullName
    throw 'Сначала восстановите журналы существующим действием и секретом зарегистрированной задачи; вручную их не удаляйте.'
}
```

Если блок обнаружил журнал, не запускайте установщик: запустите зарегистрированную задачу с её существующими действием и секретом, дождитесь восстановления, снова остановите её и повторите проверку. Если журнал сообщает об аварийном окне после `CREATE DATABASE`, но до записи OID, по существующей конфигурации задачи проверьте точное имя `temp_db`, вручную удалите только подтверждённую незавершённую временную БД и снова запустите зарегистрированную задачу; сам журнал не удаляйте. Неоднозначный, повреждённый или не соответствующий существующей конфигурации задачи журнал требует отдельного расследования без удаления БД или файла журнала.

Обычный режим:

```powershell
$ScriptDir = 'C:\Program Files\HLA_Laboratory_System\Scripts'
$TaskUser = '<ИМЯ_ПК_ИЛИ_ДОМЕНА\ИМЯ_ПОЛЬЗОВАТЕЛЯ>'
$RemoteHost = '<АДРЕС_УДАЛЁННОГО_POSTGRESQL>'
$RemoteUser = 'hla_remote_reader'
$RemoteDbName = '<ИМЯ_УДАЛЁННОЙ_БАЗЫ>'
$LocalDbName = '<ИМЯ_ЛОКАЛЬНОЙ_КОПИИ>'

if (@($TaskUser, $RemoteHost, $RemoteUser, $RemoteDbName, $LocalDbName) -match '<[^<>]+>') {
    throw 'Замените значения в угловых скобках перед запуском.'
}

$RemotePassword = Read-Host 'Пароль удалённого PostgreSQL' -AsSecureString
$LocalPassword = Read-Host 'Пароль локального PostgreSQL' -AsSecureString

try {
    & "$ScriptDir\Install-HLA-PostgresRemoteCopyTask.ps1" `
        -TaskUser $TaskUser `
        -RemoteDbHost $RemoteHost `
        -RemoteDbUser $RemoteUser `
        -RemoteDbName $RemoteDbName `
        -LocalDbName $LocalDbName `
        -RemoteDbPassword $RemotePassword `
        -LocalDbPassword $LocalPassword `
        -RefreshIntervalMinutes 60
} finally {
    if ($null -ne $RemotePassword) { $RemotePassword.Dispose() }
    if ($null -ne $LocalPassword) { $LocalPassword.Dispose() }
}
```

Двухэтапный режим:

```powershell
$ScriptDir = 'C:\Program Files\HLA_Laboratory_System\Scripts'
$TaskUser = '<ИМЯ_ПК_ИЛИ_ДОМЕНА\ИМЯ_ПОЛЬЗОВАТЕЛЯ>'
$RemoteHost = '<АДРЕС_УДАЛЁННОГО_POSTGRESQL>'
$RemoteUser = 'hla_remote_reader'

if (@($TaskUser, $RemoteHost, $RemoteUser) -match '<[^<>]+>') {
    throw 'Замените значения в угловых скобках перед запуском.'
}

$LocalPassword = Read-Host 'Пароль локального PostgreSQL' -AsSecureString

try {
    & "$ScriptDir\Install-HLA-PostgresRemoteCopyTask.ps1" `
        -TaskUser $TaskUser `
        -RemoteDbHost $RemoteHost `
        -RemoteDbUser $RemoteUser `
        -ImportDbStageMode `
        -RemoteDbPassword $RemotePassword `
        -LocalDbPassword $LocalPassword `
        -RefreshIntervalMinutes 60
} finally {
    if ($null -ne $RemotePassword) { $RemotePassword.Dispose() }

```

Если параметры `SecureString` не переданы, установщик запросит оба пароля PostgreSQL. Затем он запросит пароль Windows для `TaskUser`, создаст защищённые `Logs`, `Work`, `Secrets`, запишет новое поколение DPAPI и зарегистрирует задачу PowerShell с политикой `Bypass`. Имя единственной задачи этой роли фиксировано: `HLA PostgreSQL Remote To Local Copy`. При повторной установке установщик ещё раз проверяет неактивность задачи, удерживает свободный глобальный мьютекс, временно отключает зарегистрированную задачу на всё время ввода и регистрации и проверяет отсутствие журналов до замены; неизвестные дополнительные параметры отклоняются механизмом привязки параметров PowerShell.

Запишите напечатанный `TaskSecretPath` вида:

`C:\ProgramData\HLA_Laboratory_System\HLA_PostgresRemoteCopy\Secrets\credentials_<GUID>.json`

Заменяемый файл с секретами удаляется только после успешной замены задачи. При ошибке до регистрации или после доказанного восстановления исходного определения задачи новое поколение удаляется. При неоднозначном итоге оно сохраняется отказобезопасно, обнаруженная задача остаётся отключённой до проверки администратором, а следующая успешная установка удаляет лишние поколения.

#### 3. Выполнить `ListOnly` и первый `RunOnce`

После регистрации закройте повышенную сессию установщика. Откройте Windows PowerShell 5.1 под точным `TaskUser`, указанным при регистрации; если этой учётной записи нужны административные права для локального PostgreSQL, повышайте консоль под ней же, а не под другим администратором. Блок одинаково готов для обычного и двухэтапного режима: он проверяет `whoami` по SID, ожидаемый префикс действия PowerShell и путь к скрипту, затем повторно использует точное действие задачи со всеми нестандартными параметрами узлов, портов, пользователей, БД, интервалов и путей.

```powershell
$TaskName = 'HLA PostgreSQL Remote To Local Copy'
$ExpectedPowerShell = "$env:SystemRoot\System32\WindowsPowerShell\v1.0\powershell.exe"
$ExpectedScript = 'C:\Program Files\HLA_Laboratory_System\Scripts\HLA_Postgres_RemoteToLocal_Copy.ps1'
$Task = Get-ScheduledTask -TaskPath '\' -TaskName $TaskName -ErrorAction Stop
$Actions = @($Task.Actions)

if ($Actions.Count -ne 1) {
    throw 'У задачи ожидается ровно одно действие.'
}
$TaskAccount = New-Object System.Security.Principal.NTAccount `
    -ArgumentList ([string]$Task.Principal.UserId)
$TaskSid = $TaskAccount.Translate([System.Security.Principal.SecurityIdentifier]).Value
$CurrentIdentity = [System.Security.Principal.WindowsIdentity]::GetCurrent()
$CurrentSid = $CurrentIdentity.User.Value
$CurrentAccount = (whoami).Trim()
Write-Host "Текущая учётная запись: $CurrentAccount; SID: $CurrentSid"
if ($TaskSid -cne $CurrentSid) {
    throw "Эту проверку нужно выполнять под точным TaskUser. SID задачи: $TaskSid; текущий SID: $CurrentSid"
}

$Action = $Actions[0]
if (-not [string]::Equals(
    [System.IO.Path]::GetFullPath([string]$Action.Execute),
    [System.IO.Path]::GetFullPath($ExpectedPowerShell),
    [System.StringComparison]::OrdinalIgnoreCase
)) {
    throw 'Задача запускает неожиданный исполняемый файл.'
}

$Arguments = [string]$Action.Arguments
$StablePrefix = '-NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden '
$ExpectedPrefix = $StablePrefix + "-File `"$ExpectedScript`" "
if (-not $Arguments.StartsWith($ExpectedPrefix, [System.StringComparison]::Ordinal)) {
    throw 'Действие задачи не имеет ожидаемый безопасный префикс и основной скрипт.'
}
foreach ($Match in [regex]::Matches(
    $Arguments,
    '(?i)(?:^|\s)(?:--?|/)(?<Name>[A-Za-z][A-Za-z0-9]*)(?=$|[\s:=])'
)) {
    $Name = $Match.Groups['Name'].Value
    if ('ListOnly'.StartsWith($Name, [System.StringComparison]::OrdinalIgnoreCase) -or
        'RunOnce'.StartsWith($Name, [System.StringComparison]::OrdinalIgnoreCase)) {
        throw "В постоянном действии задачи найден одноразовый параметр: $($Match.Value.Trim())"
    }
}
$InteractiveArguments = '-NoProfile -ExecutionPolicy Bypass ' +
    $Arguments.Substring($StablePrefix.Length)

$ListOnlyProcess = Start-Process -FilePath $ExpectedPowerShell `
    -ArgumentList "$InteractiveArguments -ListOnly" `
    -NoNewWindow -Wait -PassThru
if ($ListOnlyProcess.ExitCode -ne 0) {
    throw "ListOnly завершился с ошибкой: $($ListOnlyProcess.ExitCode)"
}
if ((Read-Host 'Для реальной замены локальной БД или обеих БД этапов «до/после» введите COPY') -cne 'COPY') {
    throw 'Операция отменена.'
}
$RunOnceProcess = Start-Process -FilePath $ExpectedPowerShell `
    -ArgumentList "$InteractiveArguments -RunOnce" `
    -NoNewWindow -Wait -PassThru
if ($RunOnceProcess.ExitCode -ne 0) {
    throw "RunOnce завершился с ошибкой: $($RunOnceProcess.ExitCode)"
}
```

Проверьте вывод `ListOnly` для соединений с удалённой и локальной БД и для каждой цели; свежий `remote_copy.log` от него не создаётся. В обычном режиме `RunOnce` заменяет одну зарегистрированную локальную БД, в двухэтапном режиме последовательно обрабатывает обе точные пары. `-KeepDump` в готовый блок намеренно не входит; добавляйте его только к диагностической копии точного действия вместе с `-RunOnce`, после анализа удалите незашифрованный дамп и выполните обычный реальный запуск для очистки оставшихся файлов.

### Эксплуатационные примечания

- Каждая цель восстанавливается в уникальную временную БД и проверяется до публикации.
- До создания временной БД публикуется атомарный версионированный журнал, привязанный к `system_identifier` локального кластера, поколению и точным именам БД; после создания в нём фиксируется PostgreSQL OID временной БД.
- Если процесс аварийно завершился в узком окне после `CREATE DATABASE`, но до долговечной записи её OID, следующий запуск намеренно не доверяет найденной временной БД и не удаляет её автоматически: администратор должен проверить точное имя `temp_db` из журнала, удалить только подтверждённую незавершённую временную БД и повторить запуск; сам журнал вручную не удаляется.
- Публикация фиксирует OID текущей целевой БД, переименовывает её в строго именованную `old_db`, а новую — в целевую БД. После аварийного прерывания следующий реальный запуск по журналу и OID доказывает состояние, завершает публикацию либо восстанавливает целевое имя сохранённой БД; при неоднозначности никакая БД не удаляется.
- До любого изменения в ходе восстановления целиком проверяются все найденные журналы, их кластер, конфигурация и уникальность целей; повреждённый, чужой, не сопоставленный или дублирующий журнал глобально останавливает проход. После успешного общего допуска ошибка восстановления одного доказанно сопоставленного журнала блокирует только его цель: другая двухэтапная пара обрабатывается независимо, но общий результат прохода остаётся ошибочным и будет повторён.
- Перед новым проходом удаляются только БД `temp_db`/`old_db`, чья принадлежность доказана точным журналом и ожидаемым OID. `ListOnly` сообщает о незавершённом журнале, но не выполняет восстановление.
- Резервное и удалённое копирование одной локальной БД используют общий именованный мьютекс.
- После успешных общего допуска журналов и очистки `Work` обычная ошибка обработки одной двухэтапной пары не отменяет попытку второй; глобальная ошибка допуска или неудаляемый незашифрованный файл останавливает весь проход до создания новых дампов. При любой ошибке общий результат остаётся неуспешным и проход повторяется через `RetryMinutes`.
- `RunOnce -KeepDump` оставляет дамп только для диагностики. Запланированный наблюдатель всегда удаляет его.
- `RefreshIntervalMinutes` по умолчанию 60, `RetryMinutes` — 15.
- При неизменном SID `TaskUser` после обязательной остановки, ожидания процесса и успешного восстановления всех журналов с помощью существующей конфигурации задачи повторно запустите установщик для смены узлов, портов, пользователей PostgreSQL, их паролей, имён БД, `PgBinDir`, интервалов либо обычного или двухэтапного профиля задачи. Смена `TaskUser` требует чистого удаления и повторной установки по общему правилу выше.
- Набор DPAPI привязан к компьютеру и SID `TaskUser`; копирование файла на другой ПК не является переносом секрета.

### Функциональная проверка

Обычный режим:

```powershell
$LocalDbHost = 'localhost'
$LocalDbPort = 5432
$LocalDbUser = 'postgres'
$LocalDbName = '<ИМЯ_ЛОКАЛЬНОЙ_КОПИИ>'
if (@($LocalDbName) -match '<[^<>]+>') {
    throw 'Замените значения в угловых скобках перед запуском.'
}

Import-Module 'C:\Program Files\HLA_Laboratory_System\Scripts\Common\HLA_Operations_Common.psm1' -Force -ErrorAction Stop
$LocalPasswordSecure = Read-Host 'Пароль локального PostgreSQL' -AsSecureString
try {
    $LocalPassword = [System.Net.NetworkCredential]::new('', $LocalPasswordSecure).Password
    $Result = Invoke-HlaNativeProcessWithEnvironment -ExecutablePath 'psql.exe' -Arguments @('-h', $LocalDbHost, '-p', "$LocalDbPort", '-U', $LocalDbUser, '-d', $LocalDbName, '-v', 'ON_ERROR_STOP=1', '-c', "SELECT current_database(); SELECT COUNT(*) FROM information_schema.tables WHERE table_schema NOT IN ('pg_catalog', 'information_schema');") -EnvironmentVariables @{ PGPASSWORD = $LocalPassword }
    if ($Result.ExitCode -ne 0) { throw "Проверка локальной БД завершилась с ошибкой: $($Result.ExitCode). $($Result.OutputText)" }
    $Result.StandardError | ForEach-Object { Write-Warning $_ }
    $Result.Output | Write-Output
} finally {
    $LocalPassword = $null
    if ($null -ne $LocalPasswordSecure) { $LocalPasswordSecure.Dispose() }
}
```

Двухэтапный режим — готовый проход по обеим точным целям:

```powershell
$LocalDbHost = 'localhost'
$LocalDbPort = 5432
$LocalDbUser = 'postgres'
$LocalDbNames = @('hla_db_before', 'hla_db_after')
Import-Module 'C:\Program Files\HLA_Laboratory_System\Scripts\Common\HLA_Operations_Common.psm1' -Force -ErrorAction Stop
$LocalPasswordSecure = Read-Host 'Пароль локального PostgreSQL' -AsSecureString

try {
    $LocalPassword = [System.Net.NetworkCredential]::new('', $LocalPasswordSecure).Password
    foreach ($LocalDbName in $LocalDbNames) {
        $Result = Invoke-HlaNativeProcessWithEnvironment -ExecutablePath 'psql.exe' -Arguments @('-h', $LocalDbHost, '-p', "$LocalDbPort", '-U', $LocalDbUser, '-d', $LocalDbName, '-v', 'ON_ERROR_STOP=1', '-c', "SELECT current_database(); SELECT COUNT(*) FROM information_schema.tables WHERE table_schema NOT IN ('pg_catalog', 'information_schema');") -EnvironmentVariables @{ PGPASSWORD = $LocalPassword }
        if ($Result.ExitCode -ne 0) { throw "Проверка БД этапа «до/после» «$LocalDbName» завершилась с ошибкой: $($Result.ExitCode). $($Result.OutputText)" }
        $Result.StandardError | ForEach-Object { Write-Warning $_ }
        $Result.Output | Write-Output
    }
} finally {
    $LocalPassword = $null
    if ($null -ne $LocalPasswordSecure) { $LocalPasswordSecure.Dispose() }
}
```

В обоих режимах убедитесь, что приложение переподключается после публикации и видит ожидаемые данные. Для двухэтапного режима подтвердите это отдельно для контуров «до» и «после».

### Краткий контрольный список

- удалённая учётная запись чтения имеет только необходимые права;
- межсетевой экран и `pg_hba.conf` ограничивают источник;
- состояние задачи и секрет DPAPI созданы установщиком;
- командная строка, XML задачи и журналы не содержат паролей БД, `PGPASSWORD` процесса сценария не меняется, а пароль существует только в дочерней среде утилиты;
- `ListOnly` проверил обе стороны без записи;
- `RunOnce` успешно опубликовал цель и удалил незашифрованный дамп;
- `Work` не содержит оставшегося принадлежащего сценарию дампа после следующего реального изменяющего прохода;
- задача запущена под правильной учётной записью;
- в двухэтапном режиме проверены обе пары и семантика частичного успеха понятна операторам;
- `remote_copy.log` не содержит секретов.
